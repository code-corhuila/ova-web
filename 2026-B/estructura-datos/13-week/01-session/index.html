Aplicación práctica de estructuras de datos

Es hora de integrar. Resolvemos un caso realista combinando varias estructuras para ver cómo trabajan juntas en un programa de verdad. La competencia clave del corte no es conocer cada estructura, sino orquestarlas: asignar a cada parte del sistema la que la hace más simple y eficiente.

1

Descomponer un problema en operaciones y asignar estructuras.

2

3

Diseñar la solución antes de programar (del problema al modelo).

4

Integrar cola, pila, lista y mapa en un mismo sistema.

1. Del ejercicio al sistema

Hasta ahora estudiamos cada estructura por separado. En un programa real conviven varias: una para almacenar, otra para procesar, otra para ordenar la atención. Integrarlas bien es la meta de esta sesión.

Nota

Método: divide el problema en operaciones y asigna a cada una la estructura que la hace más simple y eficiente. La solución es la composición de esas decisiones.

2. Caso: mesa de ayuda (help desk)

Un sistema de tickets de soporte debe:

  • Registrar tickets que llegan (orden de llegada).
  • Atender por orden de llegada, salvo los urgentes (prioridad).
  • Consultar el historial de un usuario (por clave).
  • Deshacer la última acción del operador.
NecesidadEstructuraPor quéCosto
Atender por llegadaColaFIFO respeta el ordenO(1)
Urgentes primeroCola de prioridadSale primero el más urgenteO(log n)
Historial por usuarioMapa → listaAcceso por clave + crecimientoO(1) + O(1)
Deshacer acciónPilaLIFO: la última primeroO(1)

3. Diseño antes de programar

Ticket --> [ Cola de entrada (o de prioridad) ] --> Operador --> [ Pila de acciones (undo) ]
                                                        |
                                                        v
                                       [ Mapa usuario -> Lista historial ]

Diseñar el flujo primero evita reescribir código: sabes qué estructura toca en cada punto y con qué costo.

4. Implementación en Java

Queue<Ticket> entrada = new LinkedList<>();               // llegada (FIFO)
PriorityQueue<Ticket> urgentes =                          // prioridad
    new PriorityQueue<>((a, b) -> b.prioridad - a.prioridad);
Deque<Accion> deshacer = new ArrayDeque<>();              // undo (LIFO)
Map<Integer, List<Ticket>> historial = new HashMap<>();   // por usuario
void registrar(Ticket t) {
    if (t.prioridad > 0) urgentes.add(t); else entrada.add(t);
    historial.computeIfAbsent(t.usuario, k -> new ArrayList<>()).add(t);
}
Ticket atender() {                                   // urgentes primero
    if (!urgentes.isEmpty()) return urgentes.poll();
    return entrada.poll();                            // luego, por llegada
}
void hacer(Accion a) { deshacer.push(a); }
Accion undo() { return deshacer.isEmpty() ? null : deshacer.pop(); }
List<Ticket> historialDe(int usuario) {
    return historial.getOrDefault(usuario, List.of());
}

Tip

Cada método usa la estructura adecuada: poll (cola) para atender, push/pop (pila) para deshacer, Map para el historial por clave y PriorityQueue para los urgentes.

5. Cómo justificar una elección

Para cada parte del sistema responde: ¿cuál es la operación dominante? y ¿qué costo tiene en la estructura elegida? Una justificación sólida menciona ambas cosas ("uso una cola porque atiendo por llegada y poll es O(1)").

6. Errores comunes

  • Programar sin diseñar el flujo → reescrituras y estructuras mal encajadas.
  • Usar una sola estructura "para todo" aunque las operaciones difieran.
  • Recorrer una lista para buscar el historial de un usuario en vez de un mapa.
  • Simular prioridad ordenando la cola completa en cada inserción (usa PriorityQueue).
