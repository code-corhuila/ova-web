Final presentation and documentation

A system nobody can understand or explain has little value. As the last programming course, you finish like a professional: presenting your distributed system to stakeholders and documenting it so another team could operate and extend it. This session covers the presentation narrative and the documentation set that make your work credible and usable.

1

Structure a professional project presentation.

2

Tell the architecture story with decisions and evidence.

3

Produce the essential documentation set.

4

Prepare a demo that proves it works and operates.

1. The presentation is part of the engineering

Note

You will present your system as you would to a stakeholder or an employer: the problem, the solution, the key decisions (with trade-offs), a working demo, and the evidence it operates. Communicating a system clearly is a senior skill — and it is graded.

2. A narrative that lands

3. Tell the architecture story

Tip

Don't list technologies — explain decisions: why these bounded contexts, why sync here and async there, why saga + outbox, what you rejected (point to the ADRs). Show one clear architecture diagram. Stakeholders remember the why, not the framework versions.

5. A path you will face in real life

Caution

Scenario — the great system, the terrible pitch. A team built a solid system but the demo is 20 slides of architecture, no running software, and no ADRs; the stakeholder leaves unconvinced. Fix: open with the problem and a live demo (place an order, show it persist, kill a service, show it recover), then a single architecture diagram and the key decisions, then metrics and lessons. Show working software first; explain second. Engineers who can also communicate get hired.

6. Common mistakes

  • Listing tech instead of explaining decisions.
  • Slides instead of a live, working demo.
  • No README/runbooks → nobody else can run it.
  • Hiding what went wrong (no honest lessons).
