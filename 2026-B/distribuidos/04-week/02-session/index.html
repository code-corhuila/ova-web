Planning — the MVP 1 sprint (contract-first, estimation, scope)

MVP 1 is next week. This planning session turns your walking skeleton into a committed sprint: design the API contract first, break the work into small tasks, estimate honestly, protect the scope, and agree on the Definition of Done so the release is real, not a demo of slides.

Design the MVP 1 API contract-first.

2

Break work into small, estimable tasks.

3

Protect scope with MoSCoW and a sprint goal.

4

Agree the Definition of Done for the release.

1. Contract-first: agree the API before coding

Note

Design the contract before implementing, so front-end, back-end and other services can work in parallel against the same promise. Write it as OpenAPI (openapi.yaml) / proto and treat it as the source of truth. Every endpoint declares method, path, request, response and errors.

POST /api/v1/orders
req:  { "customerId": "...", "items": [ { "sku": "A-1", "qty": 1 } ] }
201:  { "orderId": "...", "status": "CONFIRMED" }
409:  { "error": { "code": "OUT_OF_STOCK", "message": "A-1 unavailable" } }

2. Break it into small tasks

Note

Slice the sprint goal into tasks a person can finish in ~a day and verify. Each maps to a user story with testable acceptance criteria. Small tasks flow across the board; big tasks hide risk.

3. Estimate honestly and protect scope

Note

Estimate with story points (relative size), not hours-as-promises. Prioritize with MoSCoW — Must / Should / Could / Won't — and commit only the Musts that fit the sprint. A crisp sprint goal ("a customer can place an order for an in-stock item") is your shield against scope creep.

4. Agree the Definition of Done

Note

Before coding, agree what "done" means for MVP 1 so nobody argues at the demo. A release-grade DoD: acceptance criteria met; unit + integration tests green; the service runs in a container against a real DB; the endpoint answers the happy path and the key error (e.g. out-of-stock → 409); README/ADR updated. "MVP" reduces scope, not standards.

5. A path you will face in real life

Caution

Scenario — scope creep on day 3. Mid-sprint someone says "while we're at it, let's add discounts and a payments integration." Accepting it silently is how MVP 1 misses the release. Move: anything not in the sprint goal goes to the backlog (Should/Could), not into this sprint. Re-plan only at the next planning. Protecting the sprint is a team responsibility — and a graded behavior here.

6. Common mistakes

  • Coding before the contract exists (integration surprises).
  • Estimating in "hours" and treating them as promises.
  • Committing every Must+Should+Could → nothing finishes.
  • A vague DoD → endless "is it done?" at the review.
