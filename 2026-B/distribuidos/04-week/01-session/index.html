Building a service — structure, layers and the walking skeleton

Now we turn the design into a running service. This weekly session shows how to lay out a service by concern (domain / application / adapters), wire dependencies at the edge (DIP), and build a "walking skeleton" — the thinnest end-to-end slice that actually runs — so your team always has something demoable.

1

Lay out a service by concern (hexagonal folders).

2

Trace a request through the layers.

3

Wire dependencies at the composition root (DIP).

4

Build a walking skeleton that runs end to end.

1. Folder layout follows the architecture

Note

The directory tree should reveal the hexagon at a glance: a pure domain/, an application/ of use-cases, and adapters/ split into inbound (driving) and outbound (driven). A newcomer should find the domain, the ports and the tests in under a minute.

2. A request's journey through the layers

Note

Trace one call so the layering is concrete: the HTTP adapter receives, the use-case orchestrates, the domain decides, the repository (port) persists via its adapter.

3. Wire at the edge (composition root)

Note

The concrete adapters are chosen in one place — the composition root (main/config) — and injected into use-cases. Nothing deep in the code does new PostgresRepo(); that is Dependency Inversion in practice, and it is what makes the service testable and swappable.

var repo   = new PostgresOrderRepository(dataSource);   // outbound adapter
var useCase= new ConfirmOrder(repo);                    // inject the PORT impl
var http   = new OrderController(useCase);              // inbound adapter
// swap PostgresOrderRepository for an in-memory one in tests - no core change
repo := adapters.NewPgOrderRepo(pool)      // outbound
uc   := app.NewConfirmOrder(repo)          // inject port
h    := httpadapter.NewOrderHandler(uc)    // inbound

4. The walking skeleton

Note

A walking skeleton is the thinnest slice that runs end to end — one endpoint, through all layers, to a real database — even if it does almost nothing. It proves the wiring, the build, the container and the deploy path before you pile on features. From there you add flesh, always keeping it runnable.

Tip

This is how you honor the course's "runtime-validated" Definition of Done: the service starts against a real DB and answers one request from day one, not "it compiles".

5. A path you will face in real life

Caution

Scenario — the "big bang" integration. A team builds the domain for three weeks, the DB for two, the HTTP for one — then spends the last week trying to make them talk, and nothing runs for the demo. Fix: invert it. Build the walking skeleton first (GET /health + one real persisted entity), integrate on day one, and grow features as thin vertical slices. Integration pain paid daily is tiny; paid at the end it sinks the release.

6. Common mistakes

  • new ConcreteDependency() deep inside use-cases (breaks DIP and tests).
  • Everything in one package/file (no visible architecture; >300-line "monolith" files).
  • Building layers in isolation and integrating at the end (big-bang).
  • A service that "compiles" but was never run against a real DB.
