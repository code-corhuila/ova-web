Inter-service communication — REST, gRPC and messaging

Services are only useful when they talk. This weekly session compares the two communication modes — synchronous request/response (REST, gRPC) and asynchronous messaging (events) — with their trade-offs, then goes deep on delivery semantics and idempotency, the details that decide whether your system is correct under failure.

1. Two modes: sync vs async

Note

Synchronous = the caller waits for a reply (REST, gRPC). Simple to reason about, but it couples caller and callee in time: if the callee is slow or down, the caller suffers. Asynchronous = the caller emits a message/event and moves on (a broker delivers it). It decouples and absorbs load spikes, at the cost of eventual consistency.

2. REST — the default sync choice

Note

REST/JSON over HTTP is the ubiquitous default: human-readable, cache-friendly, great tooling. Use it for external APIs and most service-to-service calls. Weaknesses: verbose payloads, no built-in contract enforcement (mitigated by OpenAPI), one request/response at a time.

3. gRPC — sync, fast, contract-first

Note

gRPC uses a .proto contract to generate typed clients/servers and sends compact binary over HTTP/2, with streaming. Great for internal, high-throughput or low-latency service-to-service calls. Trade-off: not human-readable, needs tooling, less friendly for public/browser APIs.

service Inventory {
  rpc CheckStock (StockRequest) returns (StockReply);
}
message StockRequest { string sku = 1; }
message StockReply   { int32 available = 1; }

4. Messaging — the async backbone

Note

A broker (Kafka, RabbitMQ) carries messages between producers and consumers. Two shapes: queues (work distributed to one of N workers) and pub/sub topics (an event fan-out to many subscribers). This is how you decouple, buffer spikes, and let many contexts react to one fact.

5. Delivery semantics decide correctness

Caution

Networks lose and duplicate messages. At-most-once may lose data; at-least-once may deliver duplicates (the common broker default); exactly-once delivery does not exist end-to-end. You engineer exactly-once *processing = at-least-once + an idempotency key* + dedup. Every consumer must survive redelivery.

func Handle(ev Event) error {
    if seen(ev.ID) { return nil }          // already processed - ignore duplicate
    if err := apply(ev); err != nil { return err }  // do the effect once
    return mark(ev.ID)                      // record so retries are no-ops
}

7. A path you will face in real life

Tip

Scenario — the synchronous chain that cascades. Checkout calls Payments synchronously, which calls a slow fraud service synchronously. Under load, threads pile up waiting, pools exhaust, and the whole checkout freezes. Fix: make the non-critical step asynchronous (emit PaymentRequested, confirm later), add timeouts + circuit breaker on the sync calls that remain, and tell the user "payment pending". Choosing sync vs async per interaction is a correctness and resilience decision, not a style preference.

8. Common mistakes

  • Long synchronous chains (A→B→C→D) that cascade under load.
  • Assuming exactly-once delivery instead of idempotent processing.
  • Using events where the caller truly needs an immediate answer.
  • No timeout/retry/circuit-breaker on synchronous calls.
