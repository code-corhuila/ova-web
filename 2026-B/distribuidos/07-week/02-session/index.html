Planning — versioned contracts and contract testing

Contracts are the promises that let independent services evolve safely. This planning session formalizes your APIs and events as versioned, machine-readable contracts, defines backward-compatibility rules, and sets up consumer-driven contract testing so a change in one service can never silently break another.

1

Formalize contracts (OpenAPI, proto, event schema).

2

Apply versioning and backward-compatibility rules.

Set up consumer-driven contract testing (Pact).

Plan integration work for the sprint.

1. The contract is the API's source of truth

Note

Write the contract as a machine-readable file — openapi.yaml for REST, .proto for gRPC, a schema (JSON Schema/Avro) for events — and keep it in the docs (or the service) repo, versioned. Tools generate clients, validate requests, and test against it. If it isn't in the contract, it doesn't exist.

2. Every endpoint declares five things

Note

A complete contract entry: method + path (or event name), request shape, response shape, errors (with a standard envelope), and a version. Use consistent conventions: ISO-8601 UTC times, ?page=&limit= pagination, UUIDs, and one error envelope { "error": { "code", "message", "details", "trace_id" } }.

3. Change without breaking: compatibility rules

Caution

Services deploy independently, so you cannot update all consumers at once. Follow backward-compatible evolution: add optional fields (safe); never remove or rename a field or change its type in the same version (breaking). A breaking change means a new version (/api/v2, or event v2), with the old one deprecated (announce, Sunset header) until consumers migrate.

4. Consumer-driven contract testing (Pact)

Note

Unit tests don't catch "I changed the response and broke another team". Contract tests do: the consumer declares what it expects; that expectation (a pact) is verified against the producer in CI. If the producer breaks the promise, the producer's build fails — before it ever reaches the consumer.

5. A path you will face in real life

Caution

Scenario — the silent rename. The Inventory team renames available to qty "to be clearer" and deploys. Orders still reads available, gets null, and every checkout says out-of-stock. No test failed because each service's unit tests passed in isolation. Fix going forward: a contract with available as the agreed field, a consumer pact that Orders publishes, and CI on Inventory that fails the rename until it's done as a versioned, coordinated change. The contract turns a production outage into a red build.

6. Common mistakes

  • No machine-readable contract → integration by guesswork.
  • Breaking changes shipped in the same version.
  • Only unit tests → cross-service breaks slip through.
  • Deprecating without announcing (no version, no Sunset).
