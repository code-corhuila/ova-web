Distributed architectures — client-server, P2P, SOA, microservices

Every distributed system is a set of choices about who talks to whom and who owns what. This weekly session maps the main architectural styles — client-server, peer-to-peer, layered/N-tier, SOA and microservices — with their real trade-offs, so your team can defend the style it picks for the product. Heavy on diagrams because a picture of an architecture is worth a page of English.

1. Architecture = boundaries + communication

Note

An architecture answers two questions: how is the system split into parts (boundaries) and how do the parts communicate (contracts). Good boundaries follow business capability (a DDD bounded context), not technical layers — so a part can change and deploy on its own.

2. The styles, and when each fits

StyleIdeaFits whenWatch out for
Client-serverClients call a central serverSimple apps, one authoritySingle bottleneck / SPOF
Peer-to-peerEvery node is client + serverFile sharing, blockchains, resilienceCoordination, security
Layered / N-tierPresentation → logic → dataClassic business appsA "distributed monolith" if split badly
SOACoarse services + an ESB/busEnterprise integrationHeavy middleware, central bus
MicroservicesSmall services by capability, own dataIndependent scale & deployOperational complexity, network everywhere
Event-drivenParts react to events (async)Decoupling, spikes, auditEventual consistency, debugging

Caution

The classic failure is the distributed monolith: you split into services but they share a database and must deploy together — you paid for the network and kept all the coupling. If services can't deploy independently, they are not microservices.

3. Microservices, split by business capability

Note

Size a service by a bounded context (Orders, Payments, Inventory), each owning its data (no shared DB). Services talk only through contracts (REST/gRPC/events). This is what buys independent deploy and scale.

4. The trade-off nobody escapes

Note

Microservices trade development independence for operational complexity: now you must handle service discovery, network failures, distributed tracing, versioned contracts and data spread across stores. Start as a well-modularized monolith, extract services when a boundary and a scaling need are both real. Choosing the style is a decision you record in an ADR (adr-NNN.md) with the alternatives you rejected.

5. A path you will face in real life

Tip

Scenario — "should we split this?" Marketing wants the catalog to handle Black-Friday spikes; the rest of the shop is calm. Options: (a) scale the whole monolith (waste), (b) extract Catalog into its own service that scales alone. Reason: is Catalog a real bounded context with its own data and a real, independent scaling need? Yes → extract it (own DB, read-optimized, cache). But Orders and Payments are tightly coupled by a transaction → keep them together for now and coordinate with a Saga later. Split for a reason, not for fashion.

6. Common mistakes

  • Splitting by technical layer (a "UI service", a "DB service") instead of by capability.
  • Sharing one database across services → distributed monolith.
  • Adding a message bus/ESB "because enterprise" when a direct call suffices.
  • No ADR: nobody remembers why the architecture is the way it is.
