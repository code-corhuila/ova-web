CI/CD — pipelines and quality gates

Continuous Integration and Delivery are what let a distributed team ship many small changes safely. This weekly session covers the pipeline stages, the quality gates that make "done" mechanical, trunk-based flow with PR checks, and the DORA metrics that tell you whether your delivery is actually healthy.

1

Distinguish CI, CD (delivery) and CD (deployment).

2

Design a pipeline with blocking quality gates.

3

Protect main with PR checks (trunk-based).

4

Measure delivery health with DORA metrics.

1. CI vs CD vs CD

Note

Continuous Integration — every change is merged frequently and automatically built + tested (small batches, fast feedback). Continuous Delivery — every green build is releasable (one click to prod). Continuous Deployment — every green build auto-deploys to prod. You choose how far to automate; the pipeline is the same backbone.

2. The pipeline is the enforcer

Note

On every push/PR the pipeline runs stages; each gate must pass or the build fails (and the merge is blocked). This is how "quality" stops being a promise and becomes a machine that rejects a lie.

3. The quality gates (Definition of Done, automated)

Note

Typical blocking gates: lint + format, static type check, unit + integration + contract tests, coverage floor (declared ≤ measured), security (deps/secrets/SAST), and no `TODO`/`FIXME`/placeholders. Together they are your Definition of Done, checked by a machine on every change.

jobs:
  quality:
    steps:
      - run: make lint            # style
      - run: make typecheck       # strict types
      - run: make test            # unit + integration + contract
      - run: make coverage-check  # >= floor; declared <= measured
      - run: make scan            # deps + secrets + SAST
      - run: ./no-todo.sh         # fail on TODO/FIXME/placeholders

4. Trunk-based flow + PR checks

Note

Keep branches short-lived; open a PR; the pipeline runs the gates on the PR; a human reviews; only a green + approved PR merges. Protect main: no direct pushes, required checks, required review. This keeps main always releasable — the foundation of CD.

5. Measure delivery health: DORA

Note

The four DORA metrics tell you if your delivery is healthy: deployment frequency, lead time for changes, change failure rate, time to restore. Elite teams deploy often, with low failure and fast recovery — small batches + automation make that possible.

6. A path you will face in real life

Caution

Scenario — the broken main. Without gates, someone merges code that doesn't compile; everyone pulls it, and the whole team is blocked for hours. Fix: branch protection + required CI (build/tests/lint) on every PR, so a red build cannot merge. main stays green and releasable. The pipeline protects the team from the team — that's the point.

7. Common mistakes

  • Manual builds/tests instead of an automated pipeline.
  • Gates that warn but don't block (ignored).
  • Direct pushes to main (no PR/protection).
  • Long-lived branches → painful merges, slow feedback.
