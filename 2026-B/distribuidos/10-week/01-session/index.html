Persistence in distributed systems — saga, outbox, CQRS

Once each service owns its data, the classic single-database transaction is gone. This weekly session tackles the hard part of distributed persistence: database-per-service, keeping data consistent across services with sagas, publishing events reliably with the outbox pattern, and serving fast reads with CQRS — all under eventual consistency.

Apply database-per-service and polyglot persistence.

2

Coordinate cross-service consistency with sagas.

3

Publish events reliably with the outbox pattern.

Separate reads with CQRS and accept eventual consistency.

1. Database per service

Note

Each service owns its database; no other service reads it directly. This is what enables independent deploy, scale and schema change. It also means you can pick the right store per service (polyglot persistence): Postgres for orders, a document store for catalog, Redis for sessions.

2. No global transaction: the saga

Caution

You cannot wrap "reserve stock + charge card + confirm order" in one ACID transaction across services. Use a saga: a sequence of local transactions, each with a compensation to undo it if a later step fails. Two styles: orchestration (a coordinator drives the steps) or choreography (services react to each other's events).

3. Publish events reliably: the outbox

Caution

The dual-write problem: you save the order to the DB and publish OrderPlaced to the broker — but the process crashes between the two, so the DB has the order and no event is sent (or vice versa). The outbox pattern fixes it: write the event into an outbox table in the same DB transaction as the state change; a relay later reads the outbox and publishes. One atomic write, no lost events.

4. Fast reads: CQRS and eventual consistency

Note

CQRS separates the write model (commands, the aggregate) from the read model (queries, a denormalized view built from events). Reads are fast and tailored; the read model is eventually consistent (updated shortly after the write). Accept and design for that lag — show "processing" states, not lies.

5. A path you will face in real life

Tip

Scenario — the lost event. Orders saves the order, then the app crashes before publishing OrderPlaced; Inventory never reserves stock, and the order is stuck. Fix: the outbox — write order + outbox event in one transaction; a relay publishes reliably (at-least-once), and consumers are idempotent. Consistency across services is achieved by sagas + outbox + idempotency, never by pretending a distributed transaction exists.

6. Common mistakes

  • Trying to force one ACID transaction across services (2PC everywhere).
  • Dual-write (DB then broker) without an outbox → lost events.
  • Non-idempotent consumers under at-least-once delivery.
  • Expecting read models to be instantly consistent.
