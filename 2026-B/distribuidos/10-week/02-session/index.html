Release — shipping MVP 2 (integrated system)

Release day for MVP 2 — the close of Corte 2. MVP 1 was one service running; MVP 2 is an integrated distributed system: services communicating via contracts, data consistent across them through sagas and the outbox, config and secrets handled per environment. Today you promote it, verify it under failure, demo it, and retrospect.

1

Promote the integrated system through the environments.

2

Verify the release, including failure and consistency paths.

3

Demo the distributed system end to end.

4

Retrospect and carry the backlog to Corte 3.

1. What's different about MVP 2

Note

MVP 2 raises the bar from "a service runs" to "the system works together": multiple services, real contracts between them, cross-service consistency (saga + outbox), and per-environment config/secrets. The release must prove not just the happy path, but the failure and consistency paths.

2. Promote and tag

Note

Promote the increment develop → qa → main (per-environment HU flow), verify in qa with production-like config, then tag `v2.0.0` on main. The images built from that tag, run with prod config, are the release.

3. The MVP 2 release checklist (DoD)

  • Acceptance criteria for all committed stories met.
  • Unit + integration + contract tests green (declared coverage ≤ measured).
  • docker compose up brings the whole system up, gated by health checks.
  • A cross-service flow works end to end (e.g. place order → reserve stock → charge).
  • A failure path is proven: a step fails and the saga compensates (no money taken without stock).
  • Events are reliable (outbox), consumers idempotent (redelivery safe).
  • Config per environment; no secrets in git/images.
  • Versioned (v2.0.0), CHANGELOG + ADRs updated.

Caution

A demo that only shows the happy path is not a distributed-systems release. Show a failure: kill a service mid-flow, prove the system stays consistent (compensation runs, no partial charge). That is the real evidence.

4. Demo the system, including failure

Tip

Drive the whole journey through the gateway; show data persisted in each service's DB; then inject a failure (stop payments, or send a duplicate event) and show the saga compensates / the idempotent consumer ignores the duplicate. Point to the contracts and ADRs that make it work.

5. Retrospect → Corte 3

Note

Close Corte 2 with a retrospective focused on integration pain: flaky startup, contract mismatches, consistency bugs. Turn each into a backlog item. Corte 3 is about operating the system: observability, deployment, security, CI/CD — and the final release.

6. How MVP 2 is evaluated

Note

Beyond functionality, the release weighs architecture (contracts respected, saga/outbox correct, no shared DB), code quality (tests incl. contract/integration), and Scrum compliance (backlog, ceremonies, per-environment flow). Individual hu-status evidence in each fork feeds personal marks.

7. Common mistakes

  • Demoing only the happy path (no failure/consistency proof).
  • No version tag / CHANGELOG → not reproducible.
  • Consistency "works" only because nothing failed during the demo.
  • Skipping the retro → integration pain repeats in Corte 3.
