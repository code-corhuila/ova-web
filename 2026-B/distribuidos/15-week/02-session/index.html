Release — shipping MVP 3 (production-grade)

MVP 3 is the production-grade release: the integrated system from MVP 2, now observable, deployed with zero downtime, secured, tested under load and chaos, and shipped through a gated pipeline. Today you promote it, verify it against the full production checklist, demo it under stress, and retrospect toward the final presentation.

1. What "production-grade" means now

Note

MVP 1 ran; MVP 2 integrated; MVP 3 operates: it has observability (metrics/traces/alerts), zero-downtime deployment + rollback, security (authn/authz, secrets), and proven resilience (load + chaos). It is something you could actually put in front of real users.

2. Promote and tag v3.0.0

Note

Same discipline: promote develop → qa → main through the gated pipeline, verify in qa, tag `v3.0.0`, and deploy with your zero-downtime strategy. The pipeline is green; the release is the tagged, tested artifact.

3. The MVP 3 operability checklist

  • All acceptance criteria met; CI green (lint, types, tests, coverage, security).
  • Deploys with zero downtime; a rehearsed rollback works.
  • Observability: dashboards for the golden signals; a real alert with a runbook; distributed tracing works.
  • Security: authn/authz enforced per service; no secrets in git; deps/secret scans pass.
  • Resilience proven: a load test meets the SLO; a chaos test shows graceful degradation (saga/breaker).
  • Cross-service consistency holds under failure (outbox/idempotency).
  • Versioned v3.0.0; CHANGELOG + ADRs + runbooks updated.

Caution

The final release is judged on operability, not just features. A demo that can't survive a killed service or a load spike is not production-grade.

4. Demo under stress

Tip

Drive the full journey; open the dashboard/traces live; run a small load test and show latency staying within SLO; inject a failure (kill a service) and show the alert fire, the system degrade gracefully, and recovery. Point to the ADRs, contracts and pipeline that make it trustworthy.

5. Retrospect toward the final presentation

Note

Close the technical work with a retro: what made the system reliable, what you'd do differently, what the metrics show (DORA, SLOs). This feeds Week 16 — the final presentation and documentation, where you tell the story of the system as a professional would to a stakeholder or an employer.

6. How MVP 3 is evaluated

Note

The release weighs functionality/operability (runs, observable, resilient), code quality (tests incl. load/chaos), architecture (contracts, saga/outbox, security), and Scrum compliance across the corte. Corte 3 also adds the certification and the final project components; individual hu-status evidence feeds personal marks.

7. Common mistakes

  • Demoing features but not operability (no metrics/failure proof).
  • No rehearsed rollback; no runbook for the alert.
  • Resilience "assumed" but never load/chaos tested.
  • Release not tagged/documented → not reproducible.
