Testing at scale — contract, e2e, load and chaos

Unit tests prove a function; they do not prove a distributed system survives production. This weekly session completes your testing strategy: the pyramid adapted to distributed systems, contract and integration tests with real dependencies, end-to-end flows, and — crucially — load and chaos testing to prove resilience before your users find the limits.

1

Apply the distributed testing pyramid.

2

Use contract + integration (testcontainers) tests.

3

Run load/performance tests against SLOs.

4

Prove resilience with chaos/fault injection.

1. The pyramid, adapted for distributed systems

Note

Many fast unit tests, fewer integration tests (a service + its real DB via testcontainers), contract tests to protect service boundaries, and a few end-to-end tests of critical journeys. Add two the pyramid usually omits: load and chaos.

2. Integration with real dependencies (testcontainers)

Note

Mocks lie about the database. Testcontainers spin a real Postgres/Kafka in a container during the test, so integration tests exercise the true driver, SQL and migrations — then tear it down. This catches the bugs mocks hide.

3. Contract and e2e: protect boundaries and journeys

Note

Contract tests (Pact) keep producer/consumer compatible (week 7). End-to-end tests drive a critical journey through the running system (place order → reserve → pay → confirm). Keep e2e few (they're slow/brittle) but cover the money paths.

4. Load and performance testing

Caution

You must know your limits before users do. Load tests (k6, Gatling, JMeter) simulate traffic and measure latency/throughput/errors against your SLOs. Find the breaking point, the bottleneck (use your traces!), and verify autoscaling actually kicks in.

5. Chaos engineering: prove resilience

Note

Chaos engineering deliberately injects failure in a controlled way — kill a service, add network latency, drop messages — and verifies the system degrades gracefully (retries, circuit breakers, saga compensation, fallbacks). You designed for failure in Corte 2; here you prove it holds.

6. A path you will face in real life

Caution

Scenario — "all green, dead on launch." Every unit test passes, but on launch day the checkout collapses at 200 req/s and a payments hiccup takes the whole system down. Fix: before release, run a load test to the SLO (find the knee, fix the bottleneck the trace reveals) and a chaos test (kill payments mid-flow, confirm the saga compensates and the circuit breaker protects checkout). Passing unit tests is table stakes; resilience is proven under load and failure.

7. Common mistakes

  • Only unit tests → distributed failures ship to prod.
  • Mocking the DB instead of testcontainers (false confidence).
  • Too many brittle e2e tests (slow pipeline, flaky).
  • Never load/chaos testing → discover limits in production.
