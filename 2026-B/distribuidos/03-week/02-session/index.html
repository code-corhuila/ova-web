Planning — service design, data ownership and contracts

With your domain modeled, planning turns bounded contexts into concrete services: who owns which data, what each one promises (its contract), and how they talk without leaking each other's models. Today you design the contracts and the anti-corruption layer, and slice the first vertical feature for MVP 1.

1. One owner per piece of data

Note

The golden rule of service design: each piece of data has exactly one owning service. Others do not read its database — they ask through its contract. Shared databases are the #1 cause of the "distributed monolith". Ownership makes change safe.

2. The contract is the promise

Note

A contract states, for every operation: the method + path (or event name), the request shape, the response shape, and the errors. It is versioned and testable. Two styles: synchronous (REST/gRPC request-response) and asynchronous (publish a domain event others subscribe to).

GET /api/v1/stock/{sku}
200 -> { "sku": "A-1", "available": 42 }
404 -> { "error": { "code": "NOT_FOUND", "message": "unknown sku" } }
event: InventoryReserved  (v1)
{ "orderId": "...", "sku": "A-1", "qty": 1, "occurredAt": "2026-08-10T12:00:00Z" }

Tip

Prefer events when the caller does not need an answer now (decoupling, resilience); prefer sync when you need an immediate decision (e.g., "is there stock to reserve?").

3. Don't let another model invade yours: ACL

Note

When you consume another context (or a legacy/3rd-party system), wrap it in an Anti-Corruption Layer (ACL): a small translator that maps their model to yours, so their naming and quirks never leak into your domain.

4. Slice a vertical feature for MVP 1

Note

Plan by thin vertical slices: one small feature that goes end to end (UI/API → use-case → domain → data) and is demoable. Avoid "horizontal" sprints ("this sprint we do all the databases") — they deliver nothing usable.

Tip

MVP 1 slice example: "A customer can place an order for an in-stock item." Stories: create Order aggregate; POST /orders; call Inventory GET /stock (sync) to check; persist; return 201. Each story has testable acceptance criteria and fits the sprint.

5. A path you will face in real life

Caution

Scenario — "both services need the customer's email." Orders and Marketing both want customer data. Tempting fix: one shared customers table both read. That couples them forever. Better: one owner (say a Customers context) exposes a contract; others keep only the minimal copy they need (e.g., Marketing stores an email it received via a CustomerRegistered event). Duplication with clear ownership beats a shared table. Decide the owner now and record it (ADR).

6. Common mistakes

  • Two services writing the same table ("just this once").
  • Contracts without error shapes or versions.
  • Leaking an external/legacy model into your domain (no ACL).
  • Horizontal slices that can't be demoed at sprint review.
