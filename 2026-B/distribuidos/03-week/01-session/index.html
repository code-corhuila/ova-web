Domain-Driven Design & Hexagonal Architecture

This is the heart of a maintainable distributed system: a pure domain that knows the business, wrapped by an application layer, isolated from all I/O behind ports and adapters. This weekly session goes deep on tactical DDD (entities, value objects, aggregates, domain events) and hexagonal architecture — the two disciplines your services must follow all semester.

1

Model with tactical DDD (entity, value object, aggregate, event).

2

Apply hexagonal architecture (ports & adapters, dependency rule).

Keep the domain free of I/O and framework code.

Recognize and fix boundary violations.

1. Why model the domain at all

Note

In a distributed system the hard complexity is the business, not the plumbing. Domain-Driven Design (DDD) puts the business rules in a pure domain layer with a shared ubiquitous language (the same words in code, tests and conversation). Everything else — HTTP, DB, queues — is detail that must not leak into that core.

2. The hexagon: ports & adapters

Note

Hexagonal architecture isolates the core from the world. The core exposes ports (interfaces); the outside implements adapters. Inbound adapters drive the app (HTTP controller, message consumer); outbound adapters are driven by it (DB, external API). The dependency rule: arrows point inward — adapters → application → domain.

3. Tactical DDD building blocks

Note

Inside a bounded context you model with four pieces:

  • Value Object: no identity; equality by value; immutable (Money, Address).
  • Entity: has identity that persists through change (Order, Customer).
  • Aggregate: a cluster with a root; the only place invariants change; loaded/saved as a whole by a repository (a port).
  • Domain Event: something that happened, immutable, past tense — the currency of communication between contexts.

4. The rule that keeps it clean

Caution

The domain imports nothing from infrastructure. No @Entity JPA annotation, no pgx, no HTTP types inside domain/. If your Order needs the database to enforce a rule, the rule is in the wrong place. Repositories are interfaces in the domain, implemented in infrastructure.

package domain.orders;                 // pure domain - zero infrastructure imports
public interface OrderRepository {      // the PORT
  Optional<Order> byId(OrderId id);
  void save(Order order);              // saves the whole aggregate
}

5. A path you will face in real life

Tip

Scenario — the "anemic" model. A team ships Order as a bag of public getters/setters and puts all the rules ("can't confirm an empty order", "can't refund more than paid") in the service and controllers. Six weeks later the same rule is duplicated in three places and one copy is wrong. Fix: move invariants into the aggregate (order.confirm() throws if empty), make fields private, and let the service just orchestrate. The domain becomes the single source of truth — and the distributed edges (other services) trust it.

6. Common mistakes

  • Anemic domain: data with no behavior; rules scattered in services.
  • Infrastructure types leaking into domain/ (JPA/ORM/HTTP).
  • Aggregates too big (the whole system) or too small (no invariant to protect).
  • Reaching inside an aggregate to mutate a child instead of going through the root.
