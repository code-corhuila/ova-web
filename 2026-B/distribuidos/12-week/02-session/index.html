Planning — deployment plan, IaC and rollback

A release is only safe if the deployment is planned and reversible. This planning session designs the deployment plan for MVP 3: how artifacts are promoted and run, infrastructure as code for reproducible environments, the zero-downtime strategy, and a rehearsed rollback — turning "deploy" from a scary event into a routine.

1

Plan artifact promotion across environments.

2

Use Infrastructure as Code for reproducibility.

3

Choose a zero-downtime strategy and rollback.

4

Slice deployment work into MVP 3 stories.

1. The deployment pipeline: one artifact, promoted

Note

CI builds the image once and pushes it to a registry; the pipeline deploys that exact image to develop, then qa, then prod — each with its own config. Promotion = "run the already-tested artifact here", never "rebuild".

2. Infrastructure as Code (IaC)

Note

Don't click your way to a server (a "snowflake" nobody can reproduce). Describe infrastructure as code (declarative files: Terraform, Compose, K8s manifests), versioned in git and reviewed like any change. Recreating an environment becomes apply, not a week of manual setup — and dev/qa/prod stay in sync.

3. Choose the strategy and rehearse the rollback

Tip

Pick the zero-downtime strategy that fits (rolling for stateless services; blue-green when you need instant switch/rollback; canary for risky changes). Then rehearse the rollback before you need it: know the exact command/flag to revert, and how to verify recovery. A rollback you've never tested is a hope, not a plan.

4. Slice the deployment stories

Note

MVP 3 stories, e.g.: "CI builds and pushes a versioned image on merge to main"; "environments are created from IaC (no manual setup)"; "deploy uses blue-green with health checks"; "a documented, rehearsed rollback reverts prod in < 5 min". Each with testable acceptance criteria.

5. A path you will face in real life

Caution

Scenario — the snowflake that no one can rebuild. Prod was set up by hand months ago; the person left; qa doesn't match prod, so "works in qa" means nothing. A disk dies and there's no way to recreate the box. Fix: capture infra as code, rebuild qa/prod from it (proving reproducibility), and from then on change infra only via reviewed code. Reproducibility is what lets you deploy — and recover — with confidence.

6. Common mistakes

  • Manually configured "snowflake" servers (unreproducible).
  • Rebuilding artifacts per environment instead of promoting.
  • No rehearsed rollback (untested = doesn't exist).
  • qa that doesn't match prod (IaC drift).
