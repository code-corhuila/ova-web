Cloud deployment — models, strategies and zero-downtime

Your containers must reach real users. This weekly session maps the cloud deployment models (IaaS, PaaS, containers, serverless), shows how to run your containers in the cloud, and covers zero-downtime strategies (rolling, blue-green, canary) plus scaling — so releases are boring, reversible events.

1. Deployment models: how much do you manage?

Note

A spectrum of control vs. convenience: IaaS (you manage the VM + everything on it), containers on a managed service / orchestrator (you ship images, the platform runs them), PaaS (push code, platform builds & runs), serverless/FaaS (functions, no servers to manage). More convenience = less control; pick per need.

2. Build once, deploy the artifact

Note

Follow 12-factor build → release → run: build the image once (in CI), combine it with environment config to make a release, then run it. Never rebuild for prod. The registry image tagged v2.0.0 that passed qa is the exact thing that runs in prod.

3. Zero-downtime deployment strategies

Note

Don't stop the old version, then start the new (that's an outage). Use: Rolling — replace instances a few at a time. Blue-green — run new (green) beside old (blue), switch traffic when green is healthy, keep blue for instant rollback. Canary — route a small % to the new version first, then ramp.

4. Scale horizontally, expect failure

Note

Scale out (more instances behind a load balancer), not just up. Stateless services scale easily; state lives in databases/caches. Assume any instance can die — health checks + the orchestrator restart/replace it. Autoscale on a signal (CPU, RPS, queue depth).

5. A path you will face in real life

Caution

Scenario — the Friday manual deploy. Someone SSHes into the server, git pull, restarts by hand. It works... until they forget a step, the service is down for 10 minutes, and nobody can reproduce the running state. Fix: deploy the immutable image (the tested artifact) via an automated, repeatable pipeline; use rolling or blue-green for zero downtime; keep the previous version for instant rollback. Manual deploys don't scale and aren't reproducible.

6. Common mistakes

  • Rebuilding a different artifact for prod (not the tested one).
  • Stop-old-then-start-new (self-inflicted downtime).
  • Manual, non-reproducible deploys.
  • Scaling only vertically; stateful services that can't scale out.
