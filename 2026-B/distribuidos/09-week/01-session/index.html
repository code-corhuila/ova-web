Configuration, secrets and feature flags

As the system grows across environments, configuration and secrets become a source of outages and breaches if handled naively. This weekly session goes deep: strict 12-factor config, secret stores and rotation, validating config at startup, and using feature flags to ship safely and decouple deploy from release.

1

Manage config strictly by environment (12-factor).

2

Handle secrets with a store (never in git) and rotate them.

3

Validate required config at startup (fail fast).

4

Use feature flags to decouple deploy from release.

1. Config strictly by environment

Note

The same image runs everywhere; only environment values change. No if (env == "prod") branches, no hard-coded hosts. Configuration is read from the environment at startup, documented in a .env.example, and validated before the service accepts traffic.

2. Secrets: never in git, rotate often

Caution

A committed secret is a breach even after you delete it (it lives in git history). Keep secrets in a secret store / manager (Vault, cloud secrets), inject them as env at run time, scope them per environment, and rotate them regularly. Never log a secret.

3. Validate config at startup (fail fast)

Note

A missing or malformed variable should stop the service immediately with a clear message — not fail mysteriously an hour later. Validate all required config on boot; a service that starts with bad config is a trap.

func mustEnv(k string) string {
    v := os.Getenv(k)
    if v == "" { log.Fatalf("missing required env: %s", k) } // stop now, clearly
    return v
}
dbURL := mustEnv("DB_URL"); jwtSecret := mustEnv("JWT_SECRET")

4. Feature flags: deploy ≠ release

Note

A feature flag wraps new behavior in a switch. You can deploy code to prod with the flag off (dormant), then release by turning it on — for everyone or a % of users (canary). Flags enable safe rollout, instant rollback (flip off), and trunk-based development.

5. A path you will face in real life

Caution

Scenario — the 2 a.m. secret leak. A developer commits a .env with the prod DB password "just to test CI". It's caught a week later — but it's in history, and the DB was internet-reachable. Fix: rotate the secret immediately, purge/rotate, add a pre-commit secret scanner and .gitignore for .env, move secrets to a store injected at runtime, and add startup validation so no one needs to paste secrets around. Prevention is process, not luck.

6. Common mistakes

  • Secrets in git / in the image / in logs.
  • if (env=="prod") logic scattered in code.
  • Silent startup with missing config (fails later, mysteriously).
  • Big-bang feature releases with no flag / no rollback path.
