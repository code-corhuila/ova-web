Planning — secure config and progressive delivery

With MVP 2 approaching, planning focuses on shipping safely: a concrete secrets-management plan, a feature-flag strategy, and a progressive delivery plan (canary + rollback) so a bad change never takes the whole system down. You turn "we should be careful" into concrete, testable stories.

1

Plan secrets ownership and rotation.

2

Define a feature-flag strategy for the product.

3

Design a canary + rollback plan.

4

Slice hardening work into MVP 2 stories.

1. A secrets plan, not good intentions

Note

Decide, per secret: who owns it, where it lives (store), how it's injected (env at runtime), who can read it (least privilege), and when it rotates. Write it down. "Be careful with secrets" is not a plan; a table with owners and rotation dates is.

2. Feature-flag strategy

Note

Agree the rules so flags don't become permanent spaghetti: name them clearly, record each flag's owner and removal date, default new flags off, and clean them up once the feature is fully released. Flags are temporary switches, not architecture.

3. Progressive delivery: canary + rollback

Note

Don't flip a risky feature on for 100% of users at once. Canary: enable for a small % (or internal users), watch the metrics, then ramp up. If something breaks, roll back instantly by flipping the flag off — no redeploy. Every risky change needs a defined rollback.

4. Slice the hardening stories

Tip

MVP 2 stories, for example: "All required config is validated at startup (fail fast)"; "Secrets are injected from the store; none in git (scanner in CI)"; "Feature X ships behind a flag defaulted off, with a canary plan"; "A documented rollback flips the flag off in < 1 minute". Each with testable acceptance criteria.

5. A path you will face in real life

Caution

Scenario — the all-or-nothing release. The team merges a big change straight to 100% of prod with no flag and no rollback plan. It has a bug; reverting means an emergency redeploy while users suffer. Fix: put it behind a flag, deploy dark, canary to 5%, watch metrics, ramp up — and if it misbehaves, flip off in seconds. Progressive delivery converts a firefight into a non-event. Plan the rollback before the release, not during the outage.

6. Common mistakes

  • A secrets "plan" that is just "don't commit them".
  • Permanent feature flags nobody removes (flag debt).
  • Releasing risky changes to 100% at once.
  • No rollback defined until the incident happens.
