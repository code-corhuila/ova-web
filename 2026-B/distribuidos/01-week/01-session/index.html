Distributed systems — models, time, consistency and trade-offs

This is the last programming course of your degree, so we start where senior engineers actually reason: not "how to add a server" but how state, time and failure change once a system spans a network. You will meet the fallacies of distributed computing, system and failure models, logical time and causality, the consistency spectrum (CAP/PACELC), replication and quorums, and the delivery semantics that make or break correctness.

1. What really changes when you cross the network

Nota

A distributed system is a set of independent nodes that communicate only by messages over an unreliable network and cooperate to appear as one coherent system. The moment you cross a process boundary you lose three things you took for granted in a monolith: shared memory/state, a single clock, and all-or-nothing failure.

Cuidado

The 8 fallacies of distributed computing (assumptions that will hurt you): the network is reliable; latency is zero; bandwidth is infinite; the network is secure; topology doesn't change; there is one administrator; transport cost is zero; the network is homogeneous. Design assuming the opposite of each.

2. System and failure models

Nota

A system model fixes your assumptions so a design can be reasoned about. Timing: synchronous (bounded message and processing delay) vs asynchronous (no bounds — the realistic model for the internet). Failure models, from easy to hard: crash-stop → crash-recovery → omission (messages dropped) → Byzantine (arbitrary/malicious).

easier  ────────────────────────────────────────────►  harder
crash-stop   crash-recovery   omission        Byzantine
(node dies)  (dies & returns) (loses msgs)    (lies / arbitrary)

Tip

Most business systems design for crash-recovery + omission over an asynchronous network. Byzantine tolerance (e.g. blockchains) is expensive — only pay for it when the threat model demands it.

3. Time is not global: logical clocks

Nota

You cannot trust wall-clock time across nodes (clock skew, NTP jumps). Ordering comes from causality, captured by Lamport's happens-before (→): if A causes B then A → B. Events with no causal path are concurrent.

class LamportClock {
  private long t = 0;
  synchronized long onLocalEvent() { return ++t; }
  synchronized long onSend()       { return ++t; }        // stamp outgoing msg
  synchronized long onReceive(long msgTs) {                // merge remote time
    t = Math.max(t, msgTs) + 1; return t;
  }
}
type Lamport struct{ mu sync.Mutex; t int64 }
func (c *Lamport) Tick() int64        { c.mu.Lock(); defer c.mu.Unlock(); c.t++; return c.t }
func (c *Lamport) Recv(ts int64) int64 {
    c.mu.Lock(); defer c.mu.Unlock()
    if ts > c.t { c.t = ts }
    c.t++; return c.t
}

Cuidado

Lamport clocks give a total order consistent with causality, but L(a) < L(b) does not prove a → b. For that you need vector clocks. Never use wall-clock timestamps to order events in a distributed protocol.

4. The consistency spectrum, CAP and PACELC

Nota

Consistency is a spectrum, not a boolean: linearizable/strong (looks like one copy, real-time order) → sequential → causal → eventual (replicas converge eventually). Stronger consistency costs coordination (latency); weaker consistency shifts complexity to the application.

Nota

CAP: under a network Partition, choose C (reject writes to stay consistent) or A (serve possibly-stale data). PACELC refines it: if Partition then C-vs-A, Else (normal operation) Latency-vs-Consistency. Real systems tune this per operation (e.g., a bank ledger = C; a "likes" counter = A/eventual).

NeedReasonable choice
Money movement, inventory decrementStrong / linearizable
User profile, catalogCausal / read-your-writes
Metrics, feeds, countersEventual

5. Replication, partitioning and quorums

Nota

Replication (copies for availability/reads) and partitioning/sharding (split data for scale) are the two axes of scaling state. With N replicas, a quorum write/read where R + W > N guarantees a read overlaps the latest write.

N = 3 replicas,  W = 2,  R = 2   → R + W = 4 > 3  ✅ (read sees latest write)
write ─► [r1]✔ [r2]✔ [r3]…        read ─► needs 2 acks → overlaps r1 or r2

Tip

Tunable quorums (à la Dynamo/Cassandra) let you trade latency vs consistency per query. W=1 is fast but risks stale/lost reads; W=N is safe but unavailable if any replica is down.

6. Consensus, in one page

Nota

Consensus = getting nodes to agree on one value/order despite failures (leader election, replicated logs). FLP impossibility: in a purely asynchronous system with even one crash, no algorithm guarantees consensus in bounded time — so real systems use timeouts/randomization to make progress in practice. Raft is the practical, teachable protocol: a leader replicates an append-only log to followers; an entry is committed once a majority acknowledges it.

        ┌─────────┐   AppendEntries   ┌─────────┐
Client ►│ Leader  │ ─────────────────►│Follower │  commit when
        │  (log)  │ ─────────────────►│Follower │  majority ACK
        └─────────┘                    └─────────┘

7. Communication & delivery semantics

Nota

Synchronous (request/response: REST, gRPC) couples caller to callee in time; asynchronous (messaging/events: Kafka, RabbitMQ) decouples them and absorbs load, at the cost of eventual consistency. Delivery guarantees: at-most-once (may lose), at-least-once (may duplicate → you MUST be idempotent), exactly-once (only as an end-to-end illusion via idempotency + dedup).

// at-least-once delivery ⇒ the same event may arrive twice.
if (processed.putIfAbsent(event.id(), TRUE) == null) {
    applyEffect(event);          // runs once per unique event id
}                                // duplicates are ignored, not double-applied

Cuidado

"Exactly-once delivery" over a network is a myth. What you build is exactly-once *processing: at-least-once delivery + an idempotency key* + deduplication/outbox. Design every consumer to survive redelivery.
