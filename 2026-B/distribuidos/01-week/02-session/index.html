Professional engineering foundations for distributed systems

The difference between code that runs and a system that survives production is discipline. As the capstone programming course, we hold a professional bar: Domain-Driven Design, hexagonal architecture with real ports and adapters (Java and Go), SOLID and Clean Code, the resilience patterns every distributed system needs (Circuit Breaker, Saga, Outbox, CQRS), a real testing strategy (contracts, testcontainers), and the way of working (Scrum, Git flow, ADRs) — plus the weekly individual deliverable that the automated grader reads from your fork.

1. The governing mindset: executable standards

Note

In serious teams, quality is mechanical, not aspirational: a spec declares, a verifier conforms. If a standard matters (a layer boundary, a coverage floor, a naming rule), it must fail the build when violated — otherwise it is just a comment. And a hard rule for this course: "MVP" reduces scope, never standards.

2. DDD — strategic and tactical

Note

Strategic DDD: split the system into bounded contexts (e.g. Orders, Payments, Inventory), each with its own ubiquitous language and model; map their relationships (context mapping). In distributed systems, a bounded context is a natural microservice boundary. Tactical DDD: inside a context use entities (identity + lifecycle), value objects (immutable, equality by value), aggregates (the only consistency/mutation boundary) and domain events (immutable, past tense).

record Money(long cents, String currency) {          // value object (immutable)
  Money { if (cents < 0) throw new IllegalArgumentException("negative"); }
  Money plus(Money o){ require(o.currency.equals(currency)); return new Money(cents+o.cents,currency); }
}
final class Order {                                   // aggregate root
  private final OrderId id; private OrderStatus status; private final List<Line> lines;
  void confirm() {                                    // invariants enforced HERE only
    if (lines.isEmpty()) throw new DomainException("empty order");
    this.status = OrderStatus.CONFIRMED;              // emits OrderConfirmed (past tense)
  }
}

Tip

The aggregate is the only place domain invariants change. Repositories load/save whole aggregates; other objects never reach inside to mutate them.

3. Hexagonal architecture (ports & adapters)

Note

The core (domain + application/use-cases) must not know how it is driven (HTTP, CLI, queue) or what it drives (DB, cache, external API). Everything I/O crosses a port (interface) implemented by an adapter. Dependency rule: adapters → application → domain, never inward-out.

interface OrderRepository { Optional<Order> byId(OrderId id); void save(Order o); }  // OUT port
final class ConfirmOrder {                                                            // use-case
  private final OrderRepository repo;                       // depends on the PORT, not JPA
  ConfirmOrder(OrderRepository repo){ this.repo = repo; }
  void handle(OrderId id){ var o = repo.byId(id).orElseThrow(); o.confirm(); repo.save(o); }
}
// out adapter implements the port; the core never imports the driver.
type PgOrderRepo struct{ db *pgxpool.Pool }
func (r *PgOrderRepo) ByID(ctx context.Context, id OrderID) (*Order, error) { /* SQL here */ }
func (r *PgOrderRepo) Save(ctx context.Context, o *Order) error            { /* SQL here */ }
// wiring (main): confirm := NewConfirmOrder(&PgOrderRepo{db}) — DIP in action

Caution

Smell test for a broken hexagon: a domain/ file that imports a driver/ORM (pgxpool, EntityManager, PrismaClient) or a controller that runs SQL. In this course that fails review.

4. SOLID and Clean Code, applied

Note

SOLID where it bites in services: SRP (one reason to change per module), DIP (depend on ports, inject adapters — never new a concrete DB client inside a use-case), OCP/ISP (small, specific ports you extend, not modify). Clean Code: honest names, small functions, no dead `TODO/FIXME` (a CI gate), explicit error handling.

func (s *Service) Confirm(ctx context.Context, id OrderID) error {
    o, err := s.repo.ByID(ctx, id)
    if err != nil { return fmt.Errorf("load order %s: %w", id, err) } // wrap, never swallow
    if err := o.Confirm(); err != nil { return err }
    return s.repo.Save(ctx, o)
}

5. Resilience patterns you will actually use

Note

Distributed calls fail; design for it.

PatternProblem it solves
Circuit BreakerStop hammering a failing dependency; fail fast, recover gracefully
Retry + backoff + jitterTransient errors, without retry storms
Timeout / BulkheadBound waiting; isolate pools so one slow dep can't sink all
SagaConsistency across services without distributed transactions (compensations)
OutboxPublish an event and commit DB state atomically (no lost events)
CQRSSeparate write model (commands) from read model (queries)
Saga (create order):  reserve stock ─► charge card ─► confirm
                          │ fail ►     compensate: release stock

6. Testing strategy (not an afterthought)

Note

Test at the cheapest level that gives confidence. Per feature we expect unit + integration + e2e, with a coverage floor and honest reporting (declared coverage may never exceed measured). For services, contract tests (Pact) protect producer/consumer compatibility; testcontainers spin a real DB in integration tests.

@Test void confirm_rejects_empty_order() {
  var order = new Order(new OrderId("1"), List.of());   // Arrange
  assertThrows(DomainException.class, order::confirm);   // Act + Assert (the contract)
}

Tip

Layout mirrors source: tests/ parallels the code; contract tests as *_contract, e2e explicit. A test asserts one behavior and was red before green.

7. Ways of working: Scrum + Git flow + ADRs

Note

Work in weekly sprints over a prioritized backlog of user stories — "As a [role], I want [action], so that [benefit]" — each with testable acceptance criteria. DoR before starting; DoD = implemented and tested, criteria met, security for critical risks, docs updated, and validated at runtime (it actually runs, DB up, service starts, no blank screen).

Note

Branch model — one HU branch per environment. The product keeps three long-lived environment branches: develop → qa → main (prod). For each user story you cut a child branch from that environment and open a Pull Request back to the same environment; then you repeat the process for the next environment. Concretely: from develop cut hu-xxx-dev and PR only to develop; from qa cut hu-xxx-qa and PR to qa; from main cut hu-xxx-main and PR to main.

git switch develop && git switch -c hu-142-dev     # child of develop
# ...work... open Pull Request:  hu-142-dev  ──►  develop
git switch qa      && git switch -c hu-142-qa      # repeat for qa
#                     open Pull Request:  hu-142-qa   ──►  qa
git switch main    && git switch -c hu-142-main    # repeat for prod
#                     open Pull Request:  hu-142-main ──►  main
feat(payments): add idempotent charge handler
fix(orders): guard against empty cart
docs(adr): adr-004 choose Saga over 2PC for checkout

Note

The team's product is a repo ecosystem, each with dev/qa/main: a `docs` repo (source of truth: architecture, ADRs adr-NNN.md, backlog), plus backend (Java/Go), database (single logical DB) and frontend (Angular/React) repos. A service is never embedded in another.

8. Your weekly individual deliverable (the fork)

Note

The team builds together, but each student proves individual contribution every week in their fork of the group repo, at the exact path `NN-week/hu-status/README.md` (a structured report: CONFIG, the HU worked, evidence links, a compliance checklist). It is graded automatically, so the structure must be exact.

Caution

Your profile repo `username/username` must carry the CONFIG block (FULL_NAME, GITHUB_USER). Without a correct match the automation cannot attribute your work — it reads as "nothing delivered". Fix it in week 1.

Tip

Duty to refute with evidence. If anyone (including the instructor) proposes something that violates these foundations, the team must refute it citing authoritative references. Evidence-based disagreement is exactly what this capstone rewards.
