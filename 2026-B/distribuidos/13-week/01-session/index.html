Security in distributed systems — authn, authz and zero trust

A distributed system has many doors, and attackers only need one. This weekly session covers authentication and authorization with tokens (JWT/OAuth2/OIDC), the gateway as the auth choke point, service-to-service trust, and a zero-trust mindset — plus the common vulnerability classes you must design against.

1

Separate authentication from authorization at scale.

2

Use tokens (JWT/OAuth2/OIDC) correctly.

3

Secure service-to-service calls (zero trust).

4

Design against common vulnerability classes.

1. Authn vs authz, again — because it matters

Note

Authentication = proving who you are (login → a token). Authorization = deciding what you may do (roles/permissions/scopes checked on each request). Authenticate once at the edge; authorize everywhere a protected action happens.

2. Tokens: JWT, OAuth2, OIDC

Note

OAuth2 is the framework for delegated access; OIDC adds identity (login) on top; the credential passed around is often a JWT — a signed token carrying claims (user id, roles, expiry). The client sends it as Authorization: Bearer <token>; services validate the signature and expiry — no DB lookup needed (stateless).

3. The gateway as choke point — but not the only guard

Caution

The API gateway is a great place to authenticate and do coarse checks, but do not trust the network behind it. Any internal service could be reached by a compromised neighbor. Each service must still verify the token and authorize the action. "Inside the firewall = safe" is a myth (that's the zero-trust lesson).

4. Service-to-service trust

Note

Services calling services must also prove identity: mTLS (mutual TLS certificates) or short-lived service tokens. Grant least privilege — each service/credential can do only what it needs. Secrets from a store, rotated (as in week 9).

5. Design against the common vulnerabilities

Note

Know the classic classes (OWASP): broken access control (the #1: missing authz checks), injection (validate/parameterize inputs), broken authentication (weak tokens/sessions), security misconfiguration (defaults, verbose errors), sensitive data exposure (encrypt in transit/at rest), SSRF. Passwords are stored hashed (bcrypt/argon2), never plaintext.

6. A path you will face in real life

Caution

Scenario — the "internal" endpoint. DELETE /admin/users has no auth "because it's only called internally". A compromised service (or an SSRF) reaches it and wipes users. Fix: every endpoint — internal or not — authenticates and authorizes; the admin route requires an ADMIN scope; service-to-service uses mTLS/least-privilege tokens. Zero trust: verify every request, everywhere.

7. Common mistakes

  • Trusting the network ("internal = safe") → no per-service authz.
  • Long-lived, over-scoped tokens; secrets in code.
  • Missing access-control checks (broken access control).
  • Storing passwords in plaintext; leaking details in errors.
