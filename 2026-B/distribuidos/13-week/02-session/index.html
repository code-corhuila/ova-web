Planning — threat modeling and the security backlog

Security is a design activity, not a scan at the end. This planning session builds a lightweight threat model of your system (STRIDE over the data-flow), turns the findings into a prioritized security backlog with testable criteria, and plans security testing into the pipeline for MVP 3.

1. Map the attack surface first

Note

Draw your system's data-flow and mark the trust boundaries (where data crosses from less-trusted to more-trusted: internet → gateway, service → DB, service → external API). Threats live at boundaries. You can't secure what you haven't mapped.

2. Find threats with STRIDE

Note

For each boundary/component, ask STRIDE: Spoofing (fake identity), Tampering (alter data), Repudiation (deny an action), Information disclosure (leak data), Denial of service, Elevation of privilege. Each maps to a mitigation you already know.

3. Turn threats into a prioritized backlog

Note

Each real threat becomes a security story with a testable acceptance criterion, prioritized by risk = likelihood × impact (P0…P3). Example: "All admin endpoints require ADMIN scope" — AC: a request without ADMIN gets 403; test in CI. Security work competes in the same backlog, not "later".

4. Plan security testing into CI

Tip

Bake security checks into the pipeline: dependency scanning (known CVEs), secret scanning, static analysis (SAST), and authz tests (a non-admin cannot hit admin routes). A finding fails the build, like any other quality gate — "a spec declares, a verifier conforms".

5. A path you will face in real life

Caution

Scenario — "we'll do a security review before launch." The review finds an IDOR (user A can read user B's orders by changing the id) two days before release; fixing it touches every service. Fix: thread the model now — STRIDE the data-flow, add authz-on-resource stories to the backlog this sprint, and add an authz test to CI so the IDOR can never ship. Security designed in is cheap; bolted on at the end is a crisis.

6. Common mistakes

  • Treating security as a final scan, not a design activity.
  • No trust boundaries mapped → blind spots.
  • Security findings with no owner/priority ("later").
  • No security gates in CI (deps/secrets/authz).
