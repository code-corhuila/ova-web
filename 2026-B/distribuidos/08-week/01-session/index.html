Agile & DevOps for distributed teams

A distributed system is built by a team that must itself work like a well-run distributed system: clear ownership, small batches, fast feedback. This weekly session covers the Scrum you will practice all semester, the DevOps culture that ties dev to operations, and the concrete rituals and metrics that keep a multi-repo, multi-service project moving.

1

Run the Scrum cycle (backlog, sprint, ceremonies).

2

Write good user stories with testable acceptance criteria.

3

Apply DevOps culture (you build it, you run it).

Use flow metrics (WIP, lead time) to improve.

1. Scrum in one picture

Note

Work flows from a prioritized product backlog into a sprint backlog, built in a fixed sprint, reviewed as a working increment, and improved in a retrospective. Roles: Product Owner (what/priority), Scrum Master (process/impediments), Team (how/build).

2. A good user story

Note

Format: "As a [role], I want [action], so that [benefit]", with acceptance criteria that are testable (a Yes/No a test can check). A story too big to finish in the sprint is split; a story without testable AC is a wish, not work. Prioritize with MoSCoW and size with story points.

HU-021  As a customer, I want to place an order for an in-stock item,
        so that I can buy it.
AC1 (testable): POST /orders with an in-stock item returns 201 + orderId.
AC2 (testable): if the item is out of stock, returns 409 OUT_OF_STOCK.
AC3 (testable): the order is persisted and retrievable by GET /orders/{id}.

3. DevOps: you build it, you run it

Note

DevOps removes the wall between "developers" and "operations": the team that builds a service also runs it — automated CI/CD, monitoring, on-call. Culture over tools: small frequent releases, automation of everything repeatable, blameless learning from failure.

4. Coordinating a distributed team

Tip

The team mirrors the system: clear ownership per service/repo (a RACI), small batches (short-lived branches, frequent PRs), fast feedback (CI on every PR), and async communication (write it down: ADRs, PR descriptions, the board) so nobody is a blocker. Trunk-ish flow + the per-environment HU branches keep integration continuous.

5. Flow metrics that actually help

Note

Measure flow, not busyness: WIP (limit work in progress — finish before starting), lead time (idea → done), cycle time, and throughput (stories/sprint). A rising WIP with falling throughput is the classic "everyone busy, nothing shipping" signal.

6. A path you will face in real life

Caution

Scenario — the hero and the bottleneck. One teammate takes 8 stories "to go faster"; three sit half-done at sprint end, and only they understand the code. Fix: enforce a WIP limit (e.g., 2 per person), pair on risky items, require PRs so knowledge spreads, and split stories so they finish. Sustainable flow beats heroics — and it is a graded behavior here (Scrum compliance).

7. Common mistakes

  • Stories without testable acceptance criteria.
  • No WIP limit → many things started, few finished.
  • "Ops is someone else's job" (breaks the DevOps loop).
  • Decisions/knowledge trapped in one head (no ADRs, no PRs).
