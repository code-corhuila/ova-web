Observability — logs, metrics and distributed tracing

When a request crosses five services, "check the logs" is not enough. This weekly session covers the three pillars of observability — structured logs, metrics and distributed traces — plus correlation IDs and the golden signals, so your team can answer "what is happening and why" in production, fast.

1. Monitoring vs observability

Note

Monitoring watches known questions ("is CPU high?"). Observability lets you ask new questions about a running system you didn't anticipate ("why are checkouts from mobile slow only for this SKU?"). In distributed systems you need observability, built on three pillars.

2. The three pillars

3. Follow one request: distributed tracing

Note

A trace follows a single request as it hops across services; each hop is a span with timing. A correlation/trace ID is generated at the edge and propagated in headers to every service, so all their logs and spans line up. Without it, cross-service debugging is guesswork.

4. Structured logs + the golden signals

Note

Log as structured JSON (level, message, trace_id, service, fields) so logs are searchable and aggregatable (ELK/Loki). For metrics, watch the golden signals: latency, traffic, errors, saturation. Alert on symptoms users feel (error rate, p99 latency), not on every CPU blip.

log.Info("order created",
  "trace_id", ctx.Value("trace_id"),
  "service", "orders", "order_id", id, "amount_cents", 1990)

5. A path you will face in real life

Tip

Scenario — "checkout is slow, users are angry." Without observability you SSH into boxes and grep. With it: the dashboard shows p99 latency spiking; a trace of a slow request shows 180ms in payments → fraud; the logs for that trace_id show fraud retrying a timing-out dependency. Root cause in minutes, not hours. In distributed systems, observability is not optional — it is how you operate.

6. Common mistakes

  • Unstructured print/plain-text logs (unsearchable at scale).
  • No correlation/trace ID → can't follow a request across services.
  • Alerting on causes (CPU) instead of symptoms (errors, latency).
  • Dashboards nobody reads / alerts that cry wolf (alert fatigue).
