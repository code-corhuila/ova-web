Planning — environments, config strategy and orchestration

Corte 2 turns your walking skeleton into an integrated system. This planning session designs how the product runs across environments (develop / qa / prod), how configuration and secrets flow without drift, and how the branch model maps to each environment — then slices the MVP 2 orchestration work into the sprint.

1

Define the environments and what differs between them.

2

Design a config/secrets strategy (12-factor).

3

Map the branch model to each environment.

4

Slice orchestration work into MVP 2 stories.

1. Environments: same artifact, different config

Note

The same image runs in every environment; only configuration changes. Three environments: develop (fast, disposable), qa (production-like, for integration/testing) and prod (real users). Promoting means "run the tested artifact with the next environment's config" — never "rebuild for prod".

2. Config & secrets: the 12-factor rule

Note

Config lives in the environment, not the code (12-factor). No environment names hard-coded, no if (env == "prod") scattered around. Secrets come from a secret store / env injection and are never committed. A new environment = a new set of env values, not a code change.

3. Branch model ↔ environment

Note

Recall the per-environment HU flow: hu-xxx-dev → PR develop, hu-xxx-qa → PR qa, hu-xxx-main → PR main (prod). Each environment branch builds and runs in its matching environment. A change reaches prod only after passing through qa — never a direct hotfix to main without the same discipline.

4. Slice the orchestration work

Tip

MVP 2 stories, for example: "All services come up with one `docker compose up` gated by health checks"; "config is read from env in every service (no hard-coded values)"; "qa environment runs the same images as develop with qa config". Each with testable acceptance criteria, sized to the sprint.

5. A path you will face in real life

Caution

Scenario — config drift. It works in develop, breaks in qa: someone hard-coded localhost:5432 in the orders service, and set a different variable name (DATABASE_URL vs DB_URL) in qa. Hours lost. Fix: one documented set of variable names used by all services; validate required vars at startup (fail fast with a clear message if missing); keep a .env.example in the repo. Config drift is a top cause of "works on dev, dies in prod".

6. Common mistakes

  • Rebuilding a different image per environment (should build once, promote).
  • Inconsistent env var names across services.
  • Secrets committed or copied into images.
  • No .env.example / no startup validation of required config.
