Docker Compose and orchestration basics

One container is easy; a distributed system is many containers that must start in the right order, find each other, stay healthy and scale. This weekly session covers Docker Compose in depth — networks, dependencies, health checks, environments and scaling — and what "orchestration" adds when you outgrow a single host.

1

Compose a multi-service system with a shared network.

2

Order startup with health checks and depends_on.

3

Externalize config per environment.

4

Understand what an orchestrator adds (and when).

1. From "a container" to "a system"

Note

Compose describes your whole system as services on a shared network, each built from an image, wired with env and volumes, and connected by service name DNS. It is your local, reproducible copy of production topology.

2. A compose file, annotated

services:
  orders-api:
    build: ./orders
    environment:
      DB_URL: postgres://db:5432/orders      # config via env
      INVENTORY_URL: http://inventory-api:8080
    depends_on:
      db: { condition: service_healthy }      # wait for a HEALTHY db
    ports: ["8080:8080"]
  db:
    image: postgres:16
    environment: { POSTGRES_DB: orders }
    volumes: ["dbdata:/var/lib/postgresql/data"]   # data survives restarts
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
volumes: { dbdata: {} }

3. Startup order is a lie you must handle

Caution

depends_on controls start order, not readiness — a container can be "started" but not yet accepting connections. Use health checks + condition: service_healthy, and make each service retry its dependencies on boot. Never assume the database is ready just because its container started.

4. One file, many environments

Note

Keep one base compose file and override per environment (docker-compose.override.yml for dev, a compose.prod.yml for prod) — different env values, resources and replicas. Secrets come from the environment or a secret store, never committed.

5. When Compose is not enough: orchestrators

Note

Compose is perfect for local/dev and small deployments on one host. When you need many hosts, self-healing (restart failed containers), rolling updates and autoscaling, you move to an orchestrator (Kubernetes). Same mental model — services, networks, config, health — at cluster scale.

6. A path you will face in real life

Tip

Scenario — "the API crashes on `docker compose up`." It works when you start the DB first by hand, but fails in CI. Cause: orders-api connected before Postgres finished initializing. Fix: add a healthcheck to db, gate orders-api with depends_on: condition: service_healthy, and add a boot retry with backoff in the service. Now up is deterministic — which is exactly what your MVP release and CI need.

7. Common mistakes

  • Relying on depends_on alone (start order ≠ readiness).
  • Hard-coding hostnames/IPs instead of service names.
  • Committing secrets / baking env into images.
  • Storing DB data outside a volume (lost on down).
