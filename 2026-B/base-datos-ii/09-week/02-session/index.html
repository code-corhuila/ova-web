Cursores, procesamiento por lotes y manejo de errores

SQL brilla trabajando en conjuntos; pero a veces necesitas procesar fila por fila (cursores) o mover millones de registros sin reventar memoria ni bloquear la base (batch). Y toda rutina seria maneja errores con transacciones. Esta sesión te da las herramientas para procesos robustos en el servidor y, sobre todo, el criterio de cuándo NO usar un cursor.

1

Explicar qué es un cursor y por qué suele ser el último recurso.

2

Preferir operaciones basadas en conjuntos sobre iteración fila a fila.

Diseñar procesamiento por lotes (batch) para grandes volúmenes.

1. Conjuntos primero, cursores después

Nota

SQL está optimizado para operar sobre conjuntos (UPDATE ... WHERE, INSERT ... SELECT). Un cursor recorre un resultado fila por fila en código procedural. Es potente, pero casi siempre más lento que la operación equivalente basada en conjuntos, porque pierde las optimizaciones del motor. Regla: si puedes expresarlo como una sentencia de conjunto, hazlo; el cursor es el último recurso.

2. Cuándo un cursor sí

Tip

Hay casos legítimos: lógica que depende del resultado de la fila anterior, integraciones que llaman a un sistema externo por registro, o procesos donde la operación de conjunto no es expresable. Incluso ahí, muchas veces una función de ventana (Semana 3) elimina la necesidad del cursor. Piensa dos veces antes de iterar.

3. Procesamiento por lotes (batch)

Cuidado

Modificar millones de filas en una sola transacción hincha el log, mantiene bloqueos por mucho tiempo y puede tumbar la sesión. La técnica: procesar por lotes (p. ej. 10.000 filas por iteración con COMMIT entre lotes), idealmente con una columna que marque el avance para reanudar si falla. Menos contención, memoria acotada y reanudable.

4. Manejo de errores y transacciones

-- Rutina robusta: transacción + captura de error
CREATE PROCEDURE transferir(p_origen BIGINT, p_destino BIGINT, p_monto NUMERIC)
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE cuenta SET saldo = saldo - p_monto WHERE id = p_origen;
  UPDATE cuenta SET saldo = saldo + p_monto WHERE id = p_destino;
EXCEPTION
  WHEN OTHERS THEN
    RAISE NOTICE 'Transferencia fallida: %', SQLERRM;  -- el motor deshace la transacción
    RAISE;                                             -- propaga para no ocultar el error
END;
$$;

Nota

Una rutina seria envuelve sus pasos en una transacción y maneja excepciones: ante un error, deshace (rollback) para no dejar datos a medias, y propaga el error (no lo silencia) para que el llamador se entere. Silenciar errores es peor que fallar: corrompe datos sin avisar.

5. Un camino que enfrentarás en la vida real

Cuidado

Escenario — "el proceso de recálculo se cae y deja la base a medias". Un procedimiento recorre 8M de filas con un cursor y las actualiza en una única transacción; a las 2 horas se agota memoria/log y aborta, revirtiendo todo (2 horas perdidas), o peor, deja datos inconsistentes por un error no manejado. Fix: (1) reemplazar el cursor por un UPDATE de conjunto o, si no se puede, procesar por lotes con commits y una marca de avance; (2) envolver cada lote en transacción con manejo de error. El proceso se vuelve rápido, acotado en memoria y reanudable. Fila‑por‑fila + transacción gigante es la receta del desastre en volúmenes grandes.

6. Errores comunes

  • Cursor donde una operación de conjunto (o función de ventana) resolvía.
  • Transacción única para millones de filas (log/bloqueos/memoria).
  • Silenciar excepciones (WHEN OTHERS THEN NULL) → corrupción silenciosa.
  • Batch sin marca de avance → no reanudable tras un fallo.
