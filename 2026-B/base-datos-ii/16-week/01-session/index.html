Diseñar un sistema de datos de extremo a extremo

Llegó el momento de juntar todo. Un sistema de datos real no elige "una" técnica: combina modelo relacional y NoSQL donde cada uno rinde, diseña para el rendimiento, protege y opera. Esta sesión te da el marco para tomar decisiones de datos de principio a fin —el núcleo del proyecto final— integrando las tres unidades del curso.

1

Elegir el/los modelo(s) de datos adecuados a cada necesidad.

2

Integrar diseño lógico, físico, seguridad y operación en una arquitectura.

3

Justificar decisiones con los trade-offs vistos en el curso.

4

Estructurar el proyecto final de datos.

1. Del requisito a la arquitectura de datos

Nota

Diseñar de extremo a extremo empieza por las necesidades de cada dato: ¿transaccional o analítico? ¿esquema fijo o variable? ¿consistencia fuerte o eventual? ¿qué volumen y escala? De ahí sale la arquitectura, que casi siempre es políglota: una relacional para el núcleo transaccional, quizá una documental para catálogos flexibles, un caché clave‑valor para lo caliente, y un almacén columnar para analítica.

2. Integrar las tres unidades

Tip

Un buen diseño de datos aplica todo el curso: U1 (diseño) — modelo normalizado, integridad, transacciones donde importan; U2 (rendimiento) — índices, plan, diseño físico, tuning; U3 (escala/operación) — NoSQL donde encaja, seguridad, respaldo/HA. No es elegir una unidad: es orquestarlas según lo que cada parte del sistema necesita.

3. Decidir con trade-offs, no con modas

Cuidado

La marca de madurez de un ingeniero de datos es justificar cada decisión con su trade‑off: "elijo relacional aquí por ACID y reportes; documental allá por esquema variable; consistencia eventual en el contador de vistas porque tolera lag; índice compuesto por este patrón de consulta; PITR por RPO≈0 en pagos". No "porque es lo que sé" ni "porque está de moda". El proyecto final se evalúa por esa justificación, no solo por que "funcione".

4. El proyecto final: estructura

Nota

Tu proyecto integra el curso sobre un dominio real (elige uno con datos ricos). Debe incluir: (1) modelo lógico normalizado + justificación; (2) DDL con integridad; (3) consultas representativas (JOINs, agregación, ventana) con su EXPLAIN; (4) al menos una decisión de NoSQL/escala argumentada; (5) plan de seguridad (roles, menor privilegio) y de respaldo (RPO/RTO); (6) un README que justifique cada decisión con sus trade‑offs. Es la evidencia de que sabes diseñar y operar datos, no solo escribir SQL.

5. Un camino que enfrentarás en la vida real

Cuidado

Escenario — la entrevista/el proyecto real. Te pedirán "diseña el sistema de datos para X". El error junior: saltar a tablas de inmediato. El enfoque senior: preguntar primero (volumen, patrones de acceso, consistencia requerida, crecimiento), y luego proponer una arquitectura justificada con trade‑offs, señalando qué se sacrifica y por qué. Diseñar datos es tomar decisiones informadas bajo restricciones, y saber explicarlas — exactamente lo que practicas en el proyecto final.

6. Errores comunes

  • Elegir el modelo por moda/costumbre y no por el requisito.
  • Diseñar sin pensar en rendimiento, seguridad y operación desde el inicio.
  • Entregar un sistema que "funciona" sin justificar decisiones.
  • Ignorar el crecimiento futuro (lo que sirve para 1.000 filas no sirve para 100M).
