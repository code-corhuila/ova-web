Teorema CAP y consistencia eventual

En cuanto los datos viven en varios servidores, aparece una ley ineludible: el teorema CAP. Ante una partición de red, un sistema distribuido debe elegir entre seguir consistente o seguir disponible; no puede tener ambas. Entender CAP —y la consistencia eventual que muchos sistemas NoSQL adoptan— te permite razonar sobre garantías reales, no promesas de marketing.

1. El teorema CAP

Nota

En un sistema distribuido no puedes garantizar a la vez las tres: Consistencia (todos ven el mismo dato), Availability/disponibilidad (toda petición responde) y Partition tolerance (funciona pese a cortes de red). El teorema dice: ante una partición (P), eliges C o A. La P no es negociable en la práctica (las redes fallan), así que la elección real es C vs A durante un corte.

2. CP vs AP: qué se sacrifica

Tip

Un sistema CP (consistencia + partición): ante un corte, prefiere rechazar operaciones antes que dar un dato inconsistente (una base bancaria dice "no puedo ahora" en vez de mostrar un saldo dudoso). Un sistema AP (disponibilidad + partición): sigue respondiendo aunque los nodos difieran temporalmente (un carrito de compras acepta el "agregar" y reconcilia después). La elección depende de qué duele más: un dato viejo o un servicio caído.

3. Consistencia eventual (ACID vs BASE)

Cuidado

Con consistencia eventual, tras una escritura los nodos convergen al mismo valor, pero por un instante una lectura puede devolver el valor anterior. Para un "me gusta" o un contador de vistas, es aceptable. Para el saldo de una cuenta o el stock en el checkout, no: ahí quieres consistencia fuerte. No es "peor": es un trade‑off que debes elegir conscientemente según el dato.

4. Un camino que enfrentarás en la vida real

Cuidado

Escenario — "el usuario ve su compra y al recargar desapareció". Un sistema AP con consistencia eventual confirma la compra en un nodo, pero la lectura siguiente pega en otro nodo que aún no replicó → parece que se perdió. Para un carrito puede tolerarse; para confirmación de pago genera pánico y tickets. Fix: usar consistencia fuerte (o "lee tus propias escrituras") para el flujo de pago, y dejar la eventual para lo que sí la tolera (recomendaciones, contadores). El error no fue elegir AP; fue aplicarlo a un dato que exigía C.

5. Errores comunes

  • Creer que un sistema puede ser C y A a la vez durante una partición.
  • Aplicar consistencia eventual a datos críticos (saldo, stock, pagos).
  • Vender "altamente consistente y siempre disponible" (CAP lo prohíbe bajo partición).
  • Ignorar el patrón "lee tus propias escrituras" cuando el usuario necesita ver su cambio.

Cierre de la sesión

CAP obliga a elegir C o A bajo partición; la consistencia eventual (BASE) escala pero admite lecturas viejas por un instante —ideal para datos tolerantes, peligrosa para críticos. Semana 13: seguridad de bases de datos, donde proteger el dato es tan importante como servirlo.
