Estrategias de JOIN y reescritura de consultas

El optimizador tiene varias formas de hacer un JOIN, y cada una gana en un escenario distinto. Entender nested loop, hash join y merge join te permite leer por qué un plan es lento y, sobre todo, escribir consultas "amables con el optimizador": predicados sargables, filtros tempranos y evitar los antipatrones que le impiden usar índices.

1

2

Escribir predicados sargables (que permiten usar índices).

1. Tres formas de unir

Tip

Nested loop: por cada fila de A busca en B (excelente si B tiene índice y A es pequeña; malísimo si ambas son grandes sin índice). Hash join: construye una tabla hash de una relación y sondea con la otra (rey para conjuntos grandes sin orden). Merge join: aprovecha datos ya ordenados. El optimizador elige; tú influyes con índices y estadísticas.

2. Predicados sargables (deja usar el índice)

Cuidado

Un predicado es sargable si el motor puede usar un índice para resolverlo. Envolver la columna en una función lo rompe: WHERE YEAR(fecha) = 2026 no usa el índice de fecha; WHERE fecha >= '2026-01-01' AND fecha < '2027-01-01' sí. Igual con WHERE precio * 1.19 > 100 (mejor precio > 100/1.19) o LIKE '%texto' (comodín inicial no usa índice B‑tree).

3. Reescribir para filtrar antes

Nota

El principio: haz menos trabajo lo antes posible. Filtra (WHERE) antes de agregar; evita SELECT * cuando solo necesitas dos columnas (habilita index‑only scans); prefiere EXISTS a IN con subconsultas grandes; y no ordenes/distingas si no hace falta. Muchas "consultas lentas" se arreglan reescribiéndolas, sin tocar índices.

4. Un camino que enfrentarás en la vida real

Cuidado

Escenario — "el índice de fecha existe pero no se usa". Un reporte diario filtra WHERE TO_CHAR(fecha,'YYYY-MM') = '2026-08'. Hay índice en fecha, pero EXPLAIN muestra Seq Scan: el predicado no es sargable (la función envuelve la columna). Fix: reescribir a un rango fecha >= '2026-08-01' AND fecha < '2026-09-01'. El mismo índice ahora sí se usa y la consulta cae de segundos a milisegundos. No faltaba un índice: faltaba escribir el predicado de forma que el índice pudiera usarse.

5. Errores comunes

  • Envolver columnas en funciones en el WHERE (rompe sargabilidad).
  • SELECT * cuando bastan pocas columnas (impide index‑only scan).
  • LIKE '%x' esperando que use índice B‑tree (el comodín inicial lo impide).
  • Ordenar/DISTINCT innecesarios que agregan costo.
