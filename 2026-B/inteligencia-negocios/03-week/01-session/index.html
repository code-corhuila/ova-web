Bases de datos transaccionales (OLTP) vs. analíticas (OLAP)

No se analiza sobre la misma base con la que se opera. Esta sesión contrasta los sistemas OLTP —hechos para registrar transacciones— con los OLAP —hechos para analizarlas—, explica por qué se separan y presenta el data warehouse como el hogar de los datos de análisis.

1. Dos mundos, dos propósitos

Nota

OLTP (Online Transaction Processing). Sistemas que registran las operaciones del día a día: una venta, un pago, un registro. Están optimizados para escribir muchos datos pequeños y rápidos, sin errores. Ejemplos: el sistema de facturación, el cajero, el CRM.

Nota

OLAP (Online Analytical Processing). Sistemas que analizan grandes volúmenes de datos históricos para responder preguntas de negocio. Están optimizados para leer y agregar (sumar, promediar, comparar) millones de filas. Es el terreno del BI.

Una factura vive en el mundo OLTP. Un reporte de "ventas por región en los últimos 3 años" vive en el mundo OLAP.

Tip

Regla mental: OLTP escribe, OLAP lee. Uno alimenta el negocio minuto a minuto; el otro lo entiende en el tiempo.

3. ¿Por qué no analizar sobre la base de producción?

Podrías pensar: "si los datos ya están en el sistema de facturación, ¿por qué no consultarlos ahí?". Tres razones lo desaconsejan:

  1. Rendimiento: una consulta analítica pesada puede frenar el sistema que factura en vivo. Nadie quiere que el análisis tumbe la caja.
  2. Estructura: la base OLTP está normalizada (partida en muchas tablas) para escribir bien, no para analizar cómodo.
  3. Historia: el sistema operativo suele borrar o sobrescribir el detalle antiguo; el análisis necesita el histórico completo.
  MUNDO OLTP                          MUNDO OLAP
  (operación)                         (análisis)
  ───────────         ETL             ───────────
  Facturación   ─────────────────→    Data
  CRM           (extraer, limpiar,    Warehouse  ───→  Dashboards
  Inventario     cargar periódico)    (histórico       y reportes
                                       organizado)

4. El data warehouse: el hogar del análisis

Nota

Data warehouse (almacén de datos). Base de datos diseñada para analizar, no para operar. Reúne datos de varias fuentes OLTP, ya limpios e integrados, y guarda el histórico organizado de forma que las consultas de negocio sean rápidas y sencillas.

El puente entre ambos mundos es el proceso ETL (Semana 7–8): extrae los datos de los sistemas operativos, los limpia y los deposita en el warehouse. Un subconjunto temático del warehouse (p. ej., solo ventas) se llama data mart.

5. Ejemplo trabajado: factura vs. reporte

Factura (OLTP)Reporte de ventas (OLAP)
Qué guardaUna compra concreta, ahora3 años de compras agregadas
Cómo se usaSe crea una vez, se consulta pocoSe consulta y filtra mil veces
Qué responde"¿Cuánto debe pagar este cliente?""¿Qué categoría creció más por región?"
Optimizado paraEscribir sin erroresLeer y sumar rápido

Ambos usan "los mismos datos", pero organizados de forma opuesta porque sirven a propósitos opuestos.

6. Errores comunes

  • Correr análisis pesados directo sobre la base de producción.
  • Creer que un data warehouse es "una copia de respaldo" (no: es una reorganización para analizar).
  • Suponer que basta una sola base para operar y analizar bien.
  • Confundir normalizado (bueno para OLTP) con dimensional (bueno para OLAP).
