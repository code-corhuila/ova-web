Diseño de base de datos y mockups

Con los requerimientos claros, diseñamos dos cosas antes de programar: cómo se guardan los datos (modelo) y cómo se ve y navega la app (mockups). Un buen diseño previo evita rehacer pantallas y estructuras a medio proyecto.

1

Modelar datos con entidades, atributos y relaciones.

2

Distinguir almacenamiento local y remoto en móvil.

3

Diferenciar wireframe, mockup y prototipo.

4

Prototipar el flujo de pantallas de la app.

1. Modelado de datos

Nota

El modelo de datos define las entidades (p. ej. Usuario, Producto), sus atributos y las relaciones entre ellas. Es el plano de cómo se guarda la información.

Usuario (id, nombre, correo)
   1 ── posee ── N   Pedido (id, fecha, total, usuario_id)
Pedido 1 ── contiene ── N  LineaPedido (producto_id, cantidad)
  • Cada entidad tiene una clave que la identifica (id).
  • Las relaciones (1‑a‑N, N‑a‑N) conectan entidades.

2. Almacenamiento local vs remoto

DóndeEjemplosPara qué
Local (en el dispositivo)SQLite, almacenamiento clave‑valorDatos offline, preferencias, caché
Remoto (en un servidor)Base de datos + API RESTDatos compartidos, sincronización entre dispositivos

Nota

Muchas apps usan ambos: guardan en local para funcionar offline y sincronizan con el servidor cuando hay conexión.

3. Wireframe, mockup y prototipo

Nota

Wireframe: boceto de baja fidelidad (cajas y texto), define estructura. Mockup: diseño de alta fidelidad (colores, tipografías), define la apariencia. Prototipo: mockups conectados que simulan la navegación.

Wireframe (estructura) → Mockup (apariencia) → Prototipo (navegación interactiva)

Herramientas típicas: Figma, Balsamiq, Adobe XD.

4. Diseñar el flujo de navegación

Antes de codificar, dibuja el mapa de pantallas: qué pantallas hay y cómo se llega de una a otra (login → inicio → detalle → …). Esto guía la implementación y detecta pantallas faltantes.

5. Errores comunes

  • Diseñar la base de datos sin los requerimientos (faltan entidades).
  • Saltar el wireframe e ir directo al mockup con colores (se pierde tiempo).
  • No pensar el caso offline cuando el requerimiento lo pide.
  • Prototipos que no reflejan el flujo real de navegación.
