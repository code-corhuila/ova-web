Fundamentos y planificación de proyectos móviles

El desarrollo móvil no empieza escribiendo código, sino entendiendo el ecosistema y planificando bien. Esta primera sesión define qué es una app, qué tipos existen (nativa, híbrida, web), cómo es el ciclo de vida de un proyecto móvil y cómo planificar un MVP con criterio.

1

Describir el ecosistema móvil (Android/iOS) y sus tiendas.

2

Distinguir apps nativas, híbridas y web/PWA con criterio.

3

Explicar el ciclo de vida de un proyecto móvil.

4

Planificar el alcance de un MVP.

1. El ecosistema móvil

Hoy dominan dos plataformas: Android (Google, lenguaje principal Kotlin/Java, tienda Google Play) e iOS (Apple, Swift/Objective‑C, App Store). Cada una tiene sus lineamientos de diseño, su proceso de publicación y su base de usuarios.

Nota

En este curso el foco práctico será el desarrollo híbrido con Ionic React (una sola base de código para varias plataformas), con una introducción a Android/Kotlin nativo y un panorama de React Native.

2. Tipos de aplicaciones

Nota

App nativa: escrita con el SDK de la plataforma (Kotlin en Android, Swift en iOS). App híbrida/multiplataforma: una base de código que corre en varias plataformas (Ionic, React Native, Flutter). Web/PWA: una web que se comporta como app en el navegador.

TipoTecnologíaRendimientoCosto/tiempoAcceso a hardware
NativaKotlin / SwiftMáximoAlto (una por plataforma)Total
HíbridaIonic, React NativeMuy buenoBajo (una base)Alto (vía plugins)
Web / PWAHTML/CSS/JSBuenoMuy bajoLimitado

Tip

No hay tipo "mejor": se elige según presupuesto, tiempo, rendimiento requerido y acceso a hardware. Un MVP suele empezar híbrido para validar rápido.

3. Ciclo de vida de un proyecto móvil

Idea → Requisitos → Diseño (UX/UI + datos) → Desarrollo → Pruebas → Despliegue (tienda) → Mantenimiento

Cada etapa alimenta a la siguiente; volver atrás cuesta más cuanto más tarde se detecta un error. Por eso planificar y prototipar temprano ahorra tiempo.

4. Planificar el MVP

Nota

MVP (Producto Mínimo Viable): la versión más pequeña de la app que resuelve el problema central y se puede probar con usuarios reales. No es una app "a medias": es lo esencial, bien hecho.

  • Define el problema y para quién.
  • Lista las funciones; separa "imprescindible" de "deseable".
  • El MVP = solo lo imprescindible.
  • Define un cronograma realista por cortes/semanas.

5. Errores comunes

  • Elegir la tecnología antes de entender el problema.
  • No delimitar el alcance (todo es "urgente") → nunca se termina.
  • Saltar el diseño/prototipo e ir directo a programar.
  • Ignorar los lineamientos de la tienda hasta el final.
