Modelamiento de datos

Antes de analizar hay que organizar. El modelamiento define cómo se estructuran los datos: entidades, atributos y relaciones. Esta sesión enseña a leer y construir un modelo entidad-relación (ERD) y a decidir entre un enfoque relacional y uno no relacional.

1. El modelo entidad-relación (ERD)

Nota

Un ERD representa las entidades (cosas: Cliente, Producto), sus atributos (nombre, precio) y las relaciones entre ellas. Es el plano de la base de datos.

Cliente (id_cliente PK, nombre, ciudad)
   1 ── realiza ── N   Pedido (id_pedido PK, fecha, id_cliente FK)
Pedido 1 ── contiene ── N  Detalle (id_pedido FK, id_producto FK, cantidad)
  • PK (clave primaria): identifica de forma única una fila.
  • FK (clave foránea): referencia la PK de otra entidad (conecta tablas).

2. Relaciones

RelaciónSignificadoEjemplo
1 : 1Uno a unoPersona ↔ Cédula
1 : NUno a muchosCliente ↔ Pedidos
N : MMuchos a muchosPedidos ↔ Productos (vía Detalle)

3. Relacional vs no relacional

Nota

Relacional (SQL): tablas con esquema fijo y relaciones (MySQL, PostgreSQL). Ideal para datos estructurados e integridad. No relacional (NoSQL): documentos/clave-valor flexibles (MongoDB). Ideal para datos variables y escala horizontal.

Relacional (tabla)          No relacional (documento JSON)
 id | nombre | ciudad        { "id":1, "nombre":"Ana",
 1  | Ana    | Neiva           "pedidos":[{"prod":"café"}] }

4. Normalización (idea básica)

Nota

Normalizar es organizar las tablas para evitar datos repetidos e inconsistencias: cada dato en un solo lugar. Reduce redundancia y errores de actualización.

Ejemplo: en vez de repetir la ciudad del cliente en cada pedido, se guarda una vez en la tabla Cliente y se referencia con la FK.

5. Errores comunes

  • No definir claves (PK/FK) → datos duplicados o inconexos.
  • Repetir información en muchas tablas (falta de normalización).
  • Usar NoSQL "porque está de moda" cuando el caso es claramente relacional.
  • Modelar sin conocer las preguntas que se responderán.
