Seguridad — autenticación y autorización con JWT

Una API real debe proteger sus datos. Esta sesión distingue autenticación (quién eres) de autorización (qué puedes hacer) y explica el patrón más usado en fullstack: iniciar sesión y recibir un token JWT que acompaña cada petición.

1

Distinguir autenticación de autorización.

2

Entender el flujo de login con JWT.

3

Proteger endpoints según el rol.

1. Autenticación vs autorización

Nota

Autenticación = verificar quién eres (login con usuario/contraseña). Autorización = decidir qué puedes hacer (permisos/roles). Primero te autenticas; luego el sistema autoriza cada acción.

2. El patrón con token (JWT)

Nota

Un JWT (JSON Web Token) es una credencial firmada que el servidor entrega al iniciar sesión. El frontend la guarda y la envía en cada petición (cabecera Authorization). El backend la valida sin guardar sesión en memoria (stateless).

1) POST /login (usuario, clave)  ─────────►  Backend verifica
2)        ◄───────────  devuelve JWT (token firmado)
3) GET /productos  Authorization: Bearer <token>  ─►  Backend valida el token
4)        ◄───────────  responde si el token es válido

3. Login y token

GET /productos
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
const { token } = await login(usuario, clave);
localStorage.setItem("token", token);
// y lo envía luego:
fetch(url, { headers: { Authorization: `Bearer ${token}` } });

4. Autorización por rol

Con Spring Security proteges rutas: por ejemplo, GET /productos para cualquier usuario autenticado, pero DELETE /productos/{id} solo para rol ADMIN.

Tip

Nunca guardes contraseñas en texto plano: se almacenan cifradas (hash). El JWT no lleva la contraseña, solo una identidad firmada con caducidad.

5. Errores comunes

  • Confundir autenticación con autorización.
  • Guardar contraseñas sin cifrar.
  • Poner el token en la URL (va en la cabecera).
  • No dar caducidad al token ni validar su firma.
