Documentación y prueba de APIs (OpenAPI/Swagger y Postman)

Una API bien hecha se documenta y se prueba. Con OpenAPI/Swagger tu API se autodescribe y se puede probar desde el navegador; con Postman envías peticiones para verificar cada endpoint antes de conectar el frontend.

Documentar la API con OpenAPI/Swagger.

Interpretar códigos de estado HTTP.

1. ¿Por qué documentar y probar?

Nota

Documentar una API permite que otros (y tu frontend) sepan qué endpoints existen, qué reciben y qué devuelven. Probar antes de integrar evita perder horas depurando por ambos lados a la vez.

2. OpenAPI / Swagger

Nota

OpenAPI es un estándar para describir APIs; Swagger UI genera una página interactiva a partir de esa descripción. En Spring Boot se agrega con una dependencia (springdoc) y expone /swagger-ui.html.

<dependency>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
</dependency>
// Se genera automaticamente:
//   /swagger-ui.html   -> UI para probar
//   /v3/api-docs       -> descripcion OpenAPI (JSON)

3. Postman

Con Postman eliges el método (GET/POST/...), la URL y el cuerpo (JSON), envías y ves la respuesta y su código de estado. Ideal para probar el backend sin frontend.

POST http://localhost:8080/productos
Body (JSON):
{ "nombre": "Teclado", "precio": 80000 }

4. Códigos de estado HTTP

CódigoSignificado
200 OKPetición correcta
201 CreatedRecurso creado
400 Bad RequestDatos inválidos
404 Not FoundNo existe
500 Server ErrorError del servidor

Tip

Devolver el código correcto ayuda al frontend a decidir qué mostrar (éxito, error de datos, no encontrado…).

5. Errores comunes

  • No documentar: el frontend no sabe cómo consumir la API.
  • Probar solo el "camino feliz" y no los errores (400/404).
  • Ignorar los códigos de estado (todo 200).
  • Integrar frontend y backend sin haber probado los endpoints.
