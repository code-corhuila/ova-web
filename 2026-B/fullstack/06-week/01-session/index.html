Introducción a Spring Boot 3 y arquitectura en capas

Empieza el backend. Spring Boot es el framework de Java para crear APIs de forma rápida. Esta sesión explica cómo se estructura un proyecto en capas (controller, service, repository, entity) para que el código quede ordenado y mantenible.

1

Entender qué es Spring Boot y para qué sirve.

2

Reconocer la arquitectura en capas de una API.

3

Identificar la responsabilidad de cada capa.

1. ¿Qué es Spring Boot?

Nota

Spring Boot (Java) permite crear una API REST con poca configuración: trae servidor embebido, autoconfiguración y dependencias listas. Con él expones endpoints que el frontend consume.

2. Arquitectura en capas

Nota

Separar el backend en capas con responsabilidades claras hace el código ordenado, testeable y fácil de cambiar: Controller (recibe la petición) → Service (lógica de negocio) → Repository (acceso a datos) → Entity (la tabla).

Petición HTTP
   │
[ Controller ]  recibe/valida, devuelve respuesta
   │
[ Service ]     reglas de negocio
   │
[ Repository ]  consulta la base de datos
   │
[ Entity ]      representa una tabla

3. Responsabilidad de cada capa

CapaResponsabilidad
ControllerRecibe la petición HTTP y responde (JSON)
ServiceContiene la lógica de negocio
RepositoryLee/escribe en la base de datos
EntityModela una tabla (fila = objeto)

Tip

Regla de oro: el controller no habla directo con la base de datos. Pasa por el service y el repository. Así cada capa se prueba y cambia por separado.

4. Estructura de un proyecto Spring Boot

com.corhuila.tienda
 ├─ controller   // ProductoController
 ├─ service      // ProductoService
 ├─ repository   // ProductoRepository
 ├─ entity       // Producto
 └─ TiendaApplication.java  // arranque
@SpringBootApplication
public class TiendaApplication {
  public static void main(String[] args) {
    SpringApplication.run(TiendaApplication.class, args);
  }
}

5. Errores comunes

  • Poner toda la lógica en el controller (capas mezcladas).
  • Que el controller acceda directo al repository saltándose el service.
  • No separar por paquetes (todo en un solo archivo).
  • Confundir la API (backend) con la interfaz (frontend).
