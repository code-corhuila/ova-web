Diseño de interfaz (mockups) y consumo de APIs desde el frontend

Antes de programar una pantalla conviene diseñarla (mockup). Y como el frontend no guarda los datos, aprenderás a pedirlos a una API con peticiones HTTP (fetch) y a mostrarlos en la interfaz.

1. Diseñar antes de codificar: mockups

Nota

Un mockup es un boceto de la pantalla (qué elementos hay y cómo se distribuyen) antes de escribir código. Ahorra retrabajo y alinea al equipo. Herramientas: Figma, papel, o bloques simples.

┌───────────────────────────┐
│  Encabezado / logo        │
├───────────────────────────┤
│  [Buscar...]     [Botón]  │
│  ┌─────────────────────┐  │
│  │ item 1              │  │
│  │ item 2              │  │  <- lista cargada desde la API
│  └─────────────────────┘  │
└───────────────────────────┘

2. Cómo se comunican frontend y backend: HTTP

Nota

El frontend hace una petición HTTP a una URL (endpoint) y el backend devuelve una respuesta, normalmente en JSON. Métodos: GET (leer), POST (crear), PUT (actualizar), DELETE (borrar).

[
  { "id": 1, "nombre": "Teclado", "precio": 80000 },
  { "id": 2, "nombre": "Mouse",   "precio": 45000 }
]

3. Consumir una API con fetch

fetch("https://api.ejemplo.com/productos")
  .then(res => res.json())
  .then(data => mostrar(data))
  .catch(err => console.error("Error:", err));
function mostrar(productos) {
  const ul = document.getElementById("lista");
  ul.innerHTML = productos
    .map(p => `<li>${p.nombre} — $${p.precio}</li>`)
    .join("");
}

Tip

Toda petición puede fallar (sin red, error del servidor). Maneja el error (catch) y el estado de carga para no dejar la pantalla en blanco.

4. Estados de la interfaz

Una vista que consume datos tiene al menos tres estados: cargando, con datos y error. Diséñalos desde el mockup.

5. Errores comunes

  • Programar sin mockup y rehacer la pantalla varias veces.
  • Olvidar res.json() (queda la respuesta sin parsear).
  • No manejar el error ni el estado de carga.
  • Suponer que los datos siempre llegan (y romper si vienen vacíos).
