Pruebas y calidad de la aplicación (testing)

El código que no se prueba se rompe en silencio. Esta sesión introduce las pruebas del backend y del frontend: unitarias (una pieza aislada) y de integración (varias piezas juntas), y buenas prácticas de calidad.

1

Distinguir prueba unitaria de integración.

2

Escribir una prueba básica de backend y de frontend.

3

Adoptar buenas prácticas de calidad.

1. ¿Por qué probar?

Nota

Las pruebas verifican automáticamente que el código hace lo que debe. Detectan errores temprano, dan confianza para cambiar (refactorizar) y documentan el comportamiento esperado.

2. Tipos de prueba

Nota

Unitaria: prueba una pieza aislada (p. ej. un método del service). De integración: prueba varias piezas juntas (p. ej. un endpoint que pasa por controller → service → repository). End-to-end (E2E): prueba el flujo completo como un usuario.

Unitaria      → una función/clase       (rápida, muchas)
Integración   → varias capas juntas     (media)
End-to-end    → toda la app como usuario (lenta, pocas)

3. Prueba de backend (JUnit)

@Test
void calculaTotalConImpuesto() {
  double total = service.totalConIva(1000);
  assertEquals(1190, total);   // 19% IVA
}

Nota

En Java se usa JUnit (y assert... para comprobar). Spring Boot facilita también pruebas de integración de los endpoints (MockMvc).

4. Prueba de frontend

test("muestra el nombre del producto", () => {
  render(<Producto nombre="Teclado" precio={80000} />);
  expect(screen.getByText(/Teclado/)).toBeInTheDocument();
});

5. Buenas prácticas de calidad

Tip

Prueba primero el camino feliz y luego los errores/límites (datos vacíos, 401, 404). Nombres de prueba claros ("qué hace y qué espera"). Automatiza las pruebas al hacer push.

6. Errores comunes

  • No probar nada y "confiar" en que funciona.
  • Probar solo el camino feliz.
  • Pruebas frágiles que dependen de datos reales cambiantes.
  • Nombres de prueba poco claros.
