Unidad 1 · Arquitectura de la app híbrida

Arquitectura de una aplicación móvil híbrida con Ionic, Capacitor y Angular

Una app móvil no fracasa por la pantalla que le falta, sino por la estructura que nadie decidió. Esta unidad te enseña a elegir el enfoque híbrido con criterio, a entender qué ocurre entre tu TypeScript y el hardware, y a dejar por escrito, antes del código, la arquitectura que tu proyecto va a respetar.

1

Definir el desarrollo móvil híbrido y compararlo con el nativo, el multiplataforma y las PWA con criterios explícitos, incluidos los casos en que no conviene.

2

Explicar la arquitectura en tiempo de ejecución de Ionic + Capacitor (interfaz, Angular, WebView, puente y API nativa) y el papel de un plugin.

3

Aplicar el método SDD y las seis secciones del marco de gobierno móvil del curso para diseñar antes de programar, con trazabilidad historia → criterio → prueba.

4

Estructurar un proyecto Ionic Angular standalone por feature, con capas presentation, domain y data y una regla de dependencias verificable.

5

Registrar la elección del framework (Angular, React o Vue) como un ADR con alternativas evaluadas y consecuencias.

6

Configurar el entorno, operar Ionic CLI y Capacitor CLI y depurar la app en navegador, emulador y dispositivo físico.

2. Desarrollo móvil híbrido

El material define el desarrollo híbrido como crear apps para iOS y Android con un solo conjunto de tecnologías web, ejecutadas en un contenedor nativo mediante un WebView. Para razonar sobre arquitectura conviene precisarlo.

Nota

Definición operativa. Una aplicación móvil híbrida es un binario nativo instalable (APK o AAB en Android, IPA en iOS) cuya interfaz y lógica se escriben con tecnologías web estándar y se ejecutan dentro de un WebView embebido. El acceso a las capacidades del dispositivo cruza un puente hacia código nativo, organizado en plugins.

  • Para la tienda y el sistema es una app nativa: se instala, se firma, pide permisos y tiene ciclo de vida; por eso el material la llama «híbrida nativa».
  • Su interfaz no son componentes del sistema: es HTML y CSS que imitan Material Design (Android) y las Human Interface Guidelines (iOS).
  • Todo lo que el WebView no ofrece cruza el puente: esa frontera concentra los costos, los riesgos y buena parte de las decisiones.

2.3 Cuándo NO elegir híbrido

  • Gráficos intensivos: juegos, 3D, realidad aumentada o animaciones complejas a 60–120 fps sostenidos.
  • Procesamiento en tiempo real del hardware: visión por computador sobre el video, audio de baja latencia, sensores a alta frecuencia.
  • Trabajo pesado en segundo plano: Bluetooth continuo o rastreo permanente, que dependen de reglas finas de cada sistema.
  • La experiencia de plataforma es el producto: widgets, extensiones, integración con el reloj o el auto.
  • APIs del sistema desde su lanzamiento, cuando aún no existe plugin y el equipo no sabe escribirlo.

Tip

La pregunta correcta no es «¿qué tecnología es mejor?», sino «¿qué requisito de mi app descarta alguna?». La Bitácora (formularios, listas, una foto, una coordenada, modo offline, dos plataformas, equipo pequeño que domina TypeScript) no supera el techo del WebView: el híbrido es defendible, y esa defensa se escribe en un ADR (sección 7). Elegirlo «porque es más barato», sin revisar qué lo descartaría, es una decisión por defecto.

3. Arquitectura en tiempo de ejecución de Ionic + Capacitor

Ionic es la capa de interfaz (componentes web que adoptan el estilo de cada plataforma), Angular estructura la aplicación (rutas, inyección de dependencias, estado) y Capacitor es el motor de ejecución nativo: empaqueta la app, aloja el WebView y ofrece el puente.

  ┌──────────────────────────────────────────────────────────────────┐
  │ UI · componentes Ionic (ion-list, ion-item, ion-modal…)          │  Web Components
  │      estilo md (Android) o ios (Apple) aplicado al ejecutar      │  + CSS por modo
  ├──────────────────────────────────────────────────────────────────┤
  │ Angular · rutas, páginas, casos de uso, DI, signals              │  TU código
  │      presentation → domain ← data                                │  TypeScript
  ├──────────────────────────────────────────────────────────────────┤
  │ WebView del sistema: sirve www/ desde un origen local            │  Android System WebView
  │                                                                  │  WKWebView (iOS)
  ╞════════════════════════ PUENTE CAPACITOR ════════════════════════╡
  │      llamada JS → mensaje serializado → método nativo → promesa  │  asíncrono
  ├──────────────────────────────────────────────────────────────────┤
  │ Plugins nativos · Kotlin/Java (Android) · Swift (iOS)            │  @capacitor/camera…
  ├──────────────────────────────────────────────────────────────────┤
  │ APIs del sistema operativo: cámara, GPS, Keystore/Keychain, red  │  permisos del SO
  └──────────────────────────────────────────────────────────────────┘

3.1 Qué pasa cuando la app pide una foto

  1. La página emite la intención «tomar foto»          presentation
  2. El caso de uso pide una Foto al puerto Camara      domain (TypeScript puro)
  3. El adaptador llama a Camera.getPhoto()             data (único que importa Capacitor)
  4. Capacitor serializa la llamada y la cruza          puente (asíncrono)
  5. El plugin nativo verifica el permiso               Kotlin / Swift
  6. El sistema muestra el diálogo y abre la cámara     sistema operativo
  7. El plugin guarda el archivo y devuelve su ruta     nativo → puente
  8. La promesa se resuelve y el estado se actualiza    data → domain → presentation
  • El puente es asíncrono y serializa: cada llamada cuesta; no se invoca un plugin en un bucle, y los datos pesados viajan como ruta de archivo, no como base64.
  • El permiso lo concede el sistema, no el WebView: se declara en AndroidManifest.xml e Info.plist y se pide en el momento de uso (Unidad 3).
  • La app se sirve desde un origen local (https://localhost en Android, capacitor://localhost en iOS): el backend debe admitirlo en su política CORS.
  • El WebView cambia según el dispositivo: en Android se actualiza desde la tienda; en iOS viaja con el sistema. La versión mínima soportada es una decisión que se registra.

3.2 Qué es un plugin

Un plugin de Capacitor es un paquete npm que expone una capacidad nativa mediante un contrato TypeScript y la implementa en cada plataforma:

ParteDónde viveQué hace
Contrato TypeScriptEl paquete npmDefine métodos y tipos; todo devuelve promesas
Implementación AndroidKotlin o JavaUsa las APIs de Android
Implementación iOSSwiftUsa las APIs de iOS
Implementación web (opcional)TypeScriptFunciona en el navegador o informa «no disponible»
Registro nativoandroid/ e ios/, tras npx cap syncGradle y Xcode lo incluyen al compilar

Los hay oficiales (@capacitor/camera, @capacitor/geolocation, @capacitor/network), comunitarios (su mantenimiento es un riesgo que se evalúa) y propios, que el material destaca: se escriben en Kotlin/Java o Swift. Así se vería uno que la Bitácora necesitaría para leer un medidor de campo con el SDK nativo de su fabricante:

import { registerPlugin } from '@capacitor/core';

export interface MedidorCampoPlugin {
  leer(opciones: { sensor: string }): Promise<{ valor: number; unidad: string }>;
}
// El nombre debe coincidir con el que registra cada implementación nativa.
export const MedidorCampo = registerPlugin<MedidorCampoPlugin>('MedidorCampo');
@CapacitorPlugin(name = "MedidorCampo")
class MedidorCampoPlugin : Plugin() {
    private val sdk = SdkFabricante()            // SDK nativo del fabricante

    @PluginMethod
    fun leer(call: PluginCall) {
        val sensor = call.getString("sensor") ?: return call.reject("Falta el sensor")
        val medida = sdk.leer(sensor)
        call.resolve(JSObject().put("valor", medida.valor).put("unidad", medida.unidad))
    }
}
// En iOS, una clase Swift (CAPPlugin) expone el mismo jsName "MedidorCampo".

Nota

Para la arquitectura, un plugin es infraestructura, igual que HttpClient. En la Bitácora ningún plugin se importa fuera de un adaptador: el dominio declara un puerto en su idioma (Camara, Ubicacion) y el adaptador lo implementa con Capacitor. La Unidad 3 desarrolla puertos, adaptadores y permisos.

Tip

La diferencia decisiva es la primera fila. En Capacitor, android/ e ios/ son código fuente del proyecto: se versionan, se revisan en los PR y cada cambio manual (permisos, íconos, firma) queda en el historial. Borrarlos y recrearlos es un error de gobierno.

4. Gobierno y SDD: el diseño precede al código

SDD (Software Design Documentation) es el método del marco de gobierno móvil del curso: la documentación de diseño precede y guía la implementación. No se documenta lo que ya se construyó; se diseña por escrito antes de programar.

  Tradicional :  código  ──►  documentación (si algún día ocurre)
  SDD         :  diseño revisado  ──►  código  ──►  documentación actualizada
                        ▲                                      │
                        └────────────── cada cambio ───────────┘
  • Diseño antes del código: un documento de diseño revisado es el requisito para empezar una feature.
  • Documentación viva: se actualiza con cada cambio; un documento desactualizado es un defecto escrito en prosa.
  • Trazabilidad: cada pantalla tiene una historia, cada historia tiene criterios y cada criterio tiene una prueba.

4.2 Definición de listo y definición de hecho

FiltroCuándo se aplicaQué exige, en lo esencialQué evita
Definición de listo (DoR)Antes de que una historia entre al sprintComo / Quiero / Para; criterios Dado / Cuando / Entonces; referencia de UI; contrato de API; estados de carga, vacío, error y sin conexión; permiso nativo identificado; estimaciónProgramar algo que nadie terminó de pensar
Definición de hecho (DoD)Antes de cerrar una historiaCriterios verificados en emulador o dispositivo; PR revisado; pruebas que pasan; regla de dependencias respetada; cuatro estados resueltos; documentación al díaEl «ya casi está» que nunca termina

Cuidado

Una historia que no cumple toda la definición de hecho no está hecha. En móvil, la casilla que más se salta es la de los estados sin conexión y de error; sin ellos, la primera visita al campo termina en una pantalla en blanco.

Un criterio bien escrito se convierte casi literalmente en una prueba, y la prueba nombra la historia: si falla en CI, dice qué promesa al usuario se rompió.

// features/visitas/domain/registrar-visita.spec.ts — igual con Jasmine o con Vitest
describe('HU-03 · Registrar visita sin señal', () => {
  it('CA-1: sin conexión, la visita queda pendiente de sincronizar', async () => {
    const repo = new VisitasEnMemoriaRepository({ enLinea: false });   // fake del contrato
    const visita = await firstValueFrom(new RegistrarVisita(repo).ejecutar(borradorValido()));
    expect(repo.pendientesDeEnvio()).toEqual([visita.id]);
  });
});

5.2 Del «por tipo» al «por feature»

El material recomienda organizar en pages/, components/, services/ y models/, y entre sus buenas prácticas pide agrupar archivos por dominio. Las dos ideas chocan cuando la app crece: con carpetas por tipo, una funcionalidad queda repartida en cuatro sitios y nada impide que todo dependa de todo. El marco resuelve el choque así:

Lo que el material llamaDónde vive en la estructura por feature
pages/features/<feature>/presentation/
components/presentation/ si es de una feature; shared/ si la usan varias y no tiene negocio
services/ con lógica de negociodomain/, como casos de uso
services/ que hablan con una APIdata/, como repositorios
services/ que guardan estado de pantallapresentation/, como ViewModel (Unidad 2)
models/ e interfaces/domain/ (entidades) y data/ (DTO): no son lo mismo
  src/app/
  ├── core/                     transversal: di/ (raíz de composición), network/ (HTTP e
  │                             interceptores), auth/ (sesión y guard), storage/, nativo/, theme/
  ├── features/
  │   ├── auth/
  │   ├── visitas/
  │   │   ├── presentation/     páginas, componentes propios, ViewModels
  │   │   ├── domain/           Visita, ListarVisitas, VisitasRepository
  │   │   └── data/             VisitasHttpRepository, VisitaDto, mapper
  │   └── ajustes/
  ├── shared/                   UI reutilizable sin lógica de negocio
  ├── app.config.ts             providers raíz
  ├── app.routes.ts             tabla central de rutas
  └── app.component.ts          ion-app + ion-router-outlet
  • Una feature = una carpeta en features/; ninguna feature importa de otra. Lo común sube a core/ o a shared/.
  • shared/ es solo UI: recibe datos por input(), emite por output() y no inyecta casos de uso ni repositorios.
  • domain/ no importa Angular, Ionic, HttpClient ni Capacitor; los plugins solo se importan dentro de un adaptador.
  • Un archivo declara un tipo principal y se llama como él; las carpetas van en kebab-case.

Tip

Prueba rápida: si borras features/ajustes/, ¿falla algo más que la ruta que la carga? Si se rompe otra feature, hay un import cruzado que no debía existir.

5.3 El arranque y la navegación, en código

La navegación del material (pila de páginas al estilo nativo, rutas y lazy loading) queda en pocos archivos. Cada loadComponent produce un fragmento de JavaScript aparte: el arranque solo descarga la estructura y el resto llega cuando se necesita. ion-router-outlet con IonicRouteStrategy mantiene las páginas en pila y respeta el botón atrás de Android y el gesto de borde de iOS. La tabla de rutas tiene un espejo en navegacion.md (sección 01).

import { bootstrapApplication } from '@angular/platform-browser';
import { AppComponent } from './app/app.component';
import { appConfig } from './app/app.config';

bootstrapApplication(AppComponent, appConfig).catch(err => console.error(err));
import { ApplicationConfig } from '@angular/core';
import { PreloadAllModules, RouteReuseStrategy, provideRouter,
         withComponentInputBinding, withPreloading } from '@angular/router';
import { provideHttpClient, withInterceptors } from '@angular/common/http';
import { IonicRouteStrategy, provideIonicAngular } from '@ionic/angular/standalone';
import { rutas } from './app.routes';
import { tokenInterceptor } from './core/network/token.interceptor';

export const appConfig: ApplicationConfig = {
  providers: [
    { provide: RouteReuseStrategy, useClass: IonicRouteStrategy },  // pila de páginas
    provideIonicAngular(),                                          // modo md o ios automático
    provideRouter(rutas, withComponentInputBinding(), withPreloading(PreloadAllModules)),
    provideHttpClient(withInterceptors([tokenInterceptor])),        // UN solo cliente HTTP

6. Capas y regla de dependencias

El material pide separar la lógica de negocio de la interfaz y evitar lógica compleja en los archivos de interfaz. La sección 01 del marco convierte ese consejo en una regla verificable: tres capas por feature y una sola dirección de dependencias.

   PRESENTATION                    DOMAIN                         DATA
  ┌─────────────────────┐        ┌─────────────────────┐        ┌───────────────────────┐
  │ VisitasListaPage    │──────► │ Visita (entidad)    │ ◄──────│ VisitasHttpRepository │
  │ ViewModel (U2)      │        │ ListarVisitas       │        │ VisitaDto + mapper    │
  └─────────────────────┘        │ VisitasRepository   │        └───────────────────────┘
   conoce Angular e Ionic        └─────────────────────┘          implementa el contrato
                                  TypeScript puro: cero dependencias hacia afuera
CapaResponsabilidadPuede depender deNunca contiene
PresentationPintar un estado y emitir intencionesDomainHttpClient, plugins, DTO del backend
DomainEntidades, casos de uso y contratos de repositorioNadaAngular, Ionic, Capacitor, HTTP
DataImplementar los contratos: red, caché, plugins y mapeoDomainComponentes, rutas, decisiones de UI

Un caso de uso es una acción de negocio (ListarVisitas, RegistrarVisita): puro, delgado y probable sin infraestructura. El repositorio es un contrato del dominio, escrito en su idioma, que la capa de datos implementa. La raíz de composición (core/di/) es el único lugar que conoce las implementaciones concretas.

6.1 Un ejemplo completo: ListarVisitas

// features/visitas/domain/ — TypeScript puro: ni @angular/* ni @capacitor/*
export type EstadoVisita = 'pendiente' | 'realizada' | 'cancelada';

export interface Visita {
  readonly id: string;
  readonly cliente: string;
  readonly fecha: Date;
  readonly estado: EstadoVisita;
}

// Clase abstracta y no interface: las interfaces desaparecen al compilar
// y no sirven como token de inyección.
export abstract class VisitasRepository {
  abstract listar(): Observable<Visita[]>;
}
// features/visitas/domain/listar-visitas.ts
export class ListarVisitas {
  constructor(private readonly repo: VisitasRepository) {}

  ejecutar(): Observable<Visita[]> {
    // Regla de negocio: la más reciente primero, sin mutar el arreglo recibido.
    return this.repo.listar().pipe(
      map(vs => [...vs].sort((a, b) => b.fecha.getTime() - a.fecha.getTime())),
    );
  }
}
// features/visitas/data/ — el DTO es el espejo del JSON y nunca sale de esta carpeta
interface VisitaDto { id: number; cliente_nombre: string; fecha_iso: string; estado: 'P' | 'R' | 'C'; }
const ESTADOS: Record<VisitaDto['estado'], EstadoVisita> = { P: 'pendiente', R: 'realizada', C: 'cancelada' };

const aVisita = (d: VisitaDto): Visita =>
  ({ id: String(d.id), cliente: d.cliente_nombre, fecha: new Date(d.fecha_iso), estado: ESTADOS[d.estado] });

@Injectable()
export class VisitasHttpRepository implements VisitasRepository {
  private readonly http = inject(HttpClient);
  private readonly api = inject(API_URL);

  listar(): Observable<Visita[]> {
    return this.http.get<VisitaDto[]>(`${this.api}/visitas`).pipe(map(dtos => dtos.map(aVisita)));
  }
}
// core/di/visitas.providers.ts — la ÚNICA línea que sabe qué implementación se usa
export const visitasProviders: Provider[] = [
  { provide: VisitasRepository, useClass: VisitasHttpRepository },
  { provide: ListarVisitas, useFactory: () => new ListarVisitas(inject(VisitasRepository)) },
];
// La página solo hace inject(ListarVisitas) y pinta el estado: cargando, listo, vacío o error.

¿Tanta ceremonia para una lista? Se cobra durante el semestre: ListarVisitas se prueba con un repositorio en memoria, sin backend; en la Unidad 2 la Bitácora agrega caché offline cambiando una línea de la raíz de composición; y si el backend renombra cliente_nombre, se tocan el DTO y el mapper, sin que el dominio ni la pantalla se enteren.

Nota

Una decisión que conviene dejar explícita. El dominio usa Observable de RxJS como tipo de asincronía: es una librería de flujos, no de infraestructura. Lo que el dominio nunca importa es @angular/*, @ionic/*, @capacitor/* ni HttpClient. Usar Promise también es defendible; lo importante es decidirlo una vez y registrarlo.

Un ADR (Architecture Decision Record) documenta una sola decisión, con las partes de la plantilla del marco: encabezado (ID, fecha, estado y autores), contexto con sus restricciones, decisión en una frase con su justificación, alternativas evaluadas con la razón del descarte, consecuencias positivas y negativas (al menos una) e impacto, y referencias. Un ADR aceptado no se borra: si la decisión cambia, se marca «Reemplazado por ADR-NNN» y se escribe uno nuevo.

  ADR-005 — Angular como framework de la app
  ──────────────────────────────────────────────────────────────────────────
  Fecha / Estado : 2026-10-09 · Aceptado · pareja del proyecto Bitácora de Campo
  Contexto       : Tres features, formularios con reglas de negocio, foto,
                   ubicación y modo offline. Debe probarse sin dispositivo y
                   mantenerse por personas que rotan. Hay que elegir antes de
                   crear el proyecto: cambiar después es reescribir la UI.
  Restricciones  : pareja con experiencia en TypeScript; cinco semanas.
  Decisión       : Angular 22 standalone (signals, inject(), control flow)
                   con @ionic/angular 9 y Capacitor 8.
  Justificación  : Desempata la DI nativa: los contratos del dominio se
                   resuelven en una raíz de composición y se cambian por fakes
                   en las pruebas sin librerías extra. Router, formularios y
                   HttpClient vienen incluidos (matriz: 54 de 60).
  Alternativas   : (a) React + @ionic/react — ecosistema enorme; descartada:
                       estado, rutas, formularios y DI se arman con librerías
                       a elegir (más ADR, más riesgo de inconsistencia).
                   (b) Vue + @ionic/vue — curva amable; descartada: provide/
                       inject más limitado para sustituir contratos en pruebas.
  Consecuencias  : + Una sola forma de hacer DI, rutas, formularios y HTTP.
                   + Casos de uso y ViewModels probables con fakes inyectados.
                   − Curva más alta (DI, RxJS, signals) para quien llegue.
                   − Una versión mayor de Angular cada seis meses: las
                     actualizaciones se planean en 05 Release.
  Verificación   : package.json fija @angular/core 22.x e @ionic/angular 9.x
                   y no contiene react ni vue.

Tip

En tu proyecto, el ADR del patrón de estado es obligatorio y se exigen al menos tres. El del framework es un candidato natural, junto con navegación, persistencia local o almacenamiento seguro de tokens. La plantilla en español está en Plantillas del proyecto.

9. Errores comunes de arquitectura

  1. Organizar por tipo técnico (`pages/`, `services/` globales). Causa: se copia la estructura de un tutorial. Corrección: estructura por feature con capas; lo común sube a core/ o shared/.
  2. Lógica de negocio en la página. Causa: el componente es el lugar más cercano. Corrección: un caso de uso en domain/; la página pinta un estado y emite intenciones.
  3. Un plugin importado en el dominio o en la página. Causa: los ejemplos de la documentación lo llaman directamente. Corrección: puerto en el dominio y adaptador en data.
  4. El DTO del backend llega a las plantillas. Causa: se tipa la respuesta HTTP y se reutiliza en todas partes. Corrección: DTO y mapper en data; la vista solo conoce la entidad.
  5. Elegir el enfoque o el framework sin ADR. Causa: «es el que conocemos» o «está de moda». Corrección: ADR con contexto, alternativas descartadas y al menos una consecuencia negativa.
  6. Tratar `android/` e `ios/` como carpetas generadas. Causa: costumbre de Cordova. Corrección: versionarlas, revisarlas en PR y documentar cada cambio manual.
  7. Validar todo en `ionic serve`. Causa: es el entorno más rápido. Corrección: lo que toca permisos o plugins se verifica en emulador o dispositivo.
  8. Programar antes de diseñar. Causa: la presión de mostrar pantallas. Corrección: SDD; el commit docs(...) va antes que el feat(...), y el historial lo demuestra.

11. Cierre y fuentes

Lo esencial de la unidad cabe en una frase: una app híbrida es una app nativa con la interfaz en un WebView, y su calidad depende de decisiones que se toman y se escriben antes del código. El enfoque se elige por descarte de requisitos; el puente marca dónde están los costos; la estructura por feature y la regla de dependencias deciden dónde vive cada pieza; y el ADR convierte cada elección en un acuerdo verificable.
