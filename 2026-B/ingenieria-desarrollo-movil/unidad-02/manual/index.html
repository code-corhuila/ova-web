Presentación y datos en capas: de la API al ViewModel (H2)

La OVA explicó en qué capa vive cada cosa; este manual lo recorre en código que ya corre. Con la app de referencia Bitácora de Campo y su API simulada vas a seguir una visita técnica desde el JSON del servidor hasta la pantalla, pasando por el mapper, la caché, los interceptores, el refresh de token y el ViewModel. Al final tendrás en tu repositorio el ADR del stack aceptado y las secciones 02 y 03 del marco, y en el foro un análisis que defiende cada decisión con evidencia.

Levantar la API simulada y la app de referencia en el navegador y en el emulador de Android, y explicar por qué el texto plano solo se permite en el build de depuración.

4

5

Publicar el análisis de la Actividad 2 con la estructura del enunciado, citas en APA 7, dos respuestas argumentadas y el PDF de entrega.

Paso 0.1 · Levanta la API simulada

Qué hacer. En api-simulada/ ejecuta npm install y npm start. Luego comprueba el contrato con el usuario y la clave de prueba que indica el README de la API:

curl -s -X POST http://localhost:3000/auth/login \
     -H "Content-Type: application/json" \
     -d '{"usuario":"<usuario-de-prueba>","clave":"<clave-de-prueba>"}'
# Copia el accessToken de la respuesta anterior
curl -s http://localhost:3000/visitas -H "Authorization: Bearer <accessToken>"

Deberías ver. El servidor anuncia API simulada en http://localhost:3000 · access 900s. El login responde accessToken, refreshToken y nombre; la segunda llamada devuelve las 30 visitas semilla. Sin Authorization, la API responde 401 con un cuerpo {error, codigo}.

Si algo salió mal. Si el puerto está ocupado, arranca con PORT=3001 npm start; si quieres los datos originales, npm run reset; si el curl con JSON falla en PowerShell, usa Git Bash.

Paso 0.3 · El ADR del stack pasa a «Aceptado»

En el H1 la pareja dejó el ADR del stack en Propuesto. El H2 lo cierra: con la arquitectura de datos y presentación diseñada, la decisión deja de ser una intención.

Qué hacer. Con la plantilla de ADR de Plantillas del proyecto:

  • Cambia Estado a «Aceptado», actualiza la Fecha y escribe la Decisión con las versiones reales de tu package.json.
  • Incluye una matriz de decisión con pesos que evalúe Angular, React y Vue con los mismos criterios.
  • Completa Alternativas evaluadas con la razón de cada descarte, y Consecuencias positivas y negativas.
  • Termina con una línea de Verificación que cualquiera pueda comprobar.

La matriz del ADR-005 de la referencia es un modelo de forma, no de contenido: tus pesos y puntajes salen de tu proyecto.

Deberías ver. Un ADR que alguien ajeno lee en tres minutos. En la referencia, la verificación es que package.json fija @angular/core 22.x y @ionic/angular 9.x y no contiene react ni vue.

1. Dominio primero: entidad, reglas, puerto y casos de uso

Si empiezas por la pantalla, el dominio termina con la forma del JSON y de los componentes. Empezando por el dominio, la red y la UI se adaptan a él. El dominio es TypeScript puro: no importa @angular/*, HttpClient, @ionic/* ni @capacitor/*, y la referencia lo hace cumplir con una regla de capas en eslint.config.js (npm run lint).

Paso 1.1 · La entidad y el puerto del repositorio

Qué hacer. Escribe la entidad con tipos del negocio (fechas como Date, coordenadas agrupadas, estados como unión de literales) y declara en el dominio qué necesita la feature, sin decir cómo se obtiene. Ese contrato es el puerto.

/** Entidad del dominio. Inmutable; usa tipos del negocio (Date, Coordenadas), no los del JSON. */
export interface Visita {
  readonly id: string;
  readonly cliente: string;
  readonly direccion: string;
  readonly estado: EstadoVisita;
  readonly observaciones: string;
  /** Foto de evidencia como data URL, o null si aún no se tomó. */
  readonly foto: string | null;
  readonly ubicacion: Coordenadas | null;
  readonly creadaEn: Date;
  readonly actualizadaEn: Date;
}

/** Lo que la persona técnica escribe o captura: la visita sin identidad ni fechas. */
export type DatosVisita = Omit<Visita, 'id' | 'creadaEn' | 'actualizadaEn'>;

/** Resultado de listar: además de las visitas, dice si vienen de la caché (offline). */
export interface ListaVisitas {
  readonly visitas: readonly Visita[];
  /** true si la red falló y estas son las últimas visitas guardadas en el dispositivo. */
  readonly desactualizado: boolean;
  /** Cuándo se obtuvieron del servidor. */
  readonly sincronizadoEn: Date;
}
/**
 * Puerto del dominio de visitas. El dominio declara QUÉ necesita; data/ decide CÓMO
 * (HTTP + caché de lectura en visitas-http.repository.ts). Los errores que lanza son de dominio.
 */
export interface VisitasRepository {
  /** Lee en línea; si no hay red devuelve la caché marcada como desactualizada. */
  listar(): Promise<ListaVisitas>;
  obtener(id: string): Promise<Visita>;
  crear(datos: DatosVisita): Promise<Visita>;
  actualizar(id: string, datos: DatosVisita): Promise<Visita>;
  eliminar(id: string): Promise<void>;
}

Deberías ver. Tres tipos con propósitos distintos: la entidad, lo que la persona escribe y el resultado de una lectura. desactualizado dice que los datos pueden venir de una caché, pero el dominio no sabe de cuál.

`Observable` en la OVA, `Promise` en la referencia. La OVA mostró el contrato del repositorio con Observable. La referencia usa Promise porque cada operación produce una sola respuesta: una lectura o una escritura, no un flujo de valores. Lo reactivo es el estado de la pantalla: un BehaviorSubject del ViewModel que la vista lee como signal con toSignal (paso 5.1). HttpClient sigue devolviendo Observable y el repositorio lo convierte con firstValueFrom. Elige una forma para todo el proyecto y regístrala en el ADR del patrón de estado.

`interface` y no clase abstracta. La OVA usó una clase abstracta porque una interfaz desaparece al compilar y no sirve como token de inyección. La referencia deja la interfaz pura en el dominio y crea el token en la raíz de composición (VISITAS_REPOSITORY, paso 2.4). Las dos formas cumplen la regla de capas.

Paso 1.2 · Reglas de negocio y casos de uso

Qué hacer. Escribe las reglas una sola vez, en el dominio, como funciones que se prueban sin Angular. En la referencia, validarDatosVisita (en domain/reglas-visita.ts) recorta espacios, verifica los límites de la constante LIMITES_VISITA (que el formulario reutiliza en el paso 5.3) y exige foto para marcar una visita como realizada; si algo falla, lanza ErrorValidacion. Luego, un caso de uso por archivo, con un método ejecutar y el puerto recibido por constructor.

/** Caso de uso: registrar una visita nueva. Valida las reglas antes de ir a la red. */
export class RegistrarVisita {
  constructor(private readonly repositorio: VisitasRepository) {}

  async ejecutar(datos: DatosVisita): Promise<Visita> {
    return this.repositorio.crear(validarDatosVisita(datos));
  }
}
/** Caso de uso: listar las visitas de la jornada, ordenadas (pendientes primero). */
export class ListarVisitas {
  constructor(private readonly repositorio: VisitasRepository) {}

  async ejecutar(): Promise<ListaVisitas> {
    const lista = await this.repositorio.listar();
    return { ...lista, visitas: ordenarParaJornada(lista.visitas) };
  }
}

La referencia tiene seis casos de uso. EliminarVisita, por ejemplo, lanza ErrorValidacion si la visita está realizada («son el registro del trabajo de campo») y no llama al repositorio: la regla vive en el dominio, no en el botón de la pantalla.

2. Datos: DTO, mapper y repositorio HTTP con caché de lectura

La capa de datos implementa el puerto del dominio. Es la única que conoce el JSON del servidor, HttpClient y el almacenamiento local; nada de esto aparece en una pantalla.

Paso 2.1 · El DTO y el mapper que valida

Qué hacer. Escribe el DTO como espejo exacto del JSON, sin «mejorarlo»: en data/visita.dto.ts, VisitaDto tiene estado: string, lat y lng sueltos y las fechas creada y actualizada como texto ISO. Después escribe el mapper DTO → entidad (data/visita.mapper.ts), que valida el contrato en el camino y falla fuerte con un error de dominio en vez de adivinar.

/**
 * DTO → dominio. Valida el contrato y transforma:
 *   estado string → EstadoVisita · creada/actualizada ISO → Date · lat/lng sueltos → ubicacion | null.
 * Si el payload no cumple el contrato lanza ErrorDatosInvalidos (fallar fuerte, no adivinar).
 */
export function aVisita(dto: unknown): Visita {
  if (!esVisitaDto(dto)) throw new ErrorDatosInvalidos('Visita con campos faltantes o de tipo incorrecto');
  if (!esEstado(dto.estado)) throw new ErrorDatosInvalidos(`Estado desconocido: ${dto.estado}`);
  const creadaEn = aFecha(dto.creada, 'creada');
  return {
    id: dto.id,
    cliente: dto.cliente,
    direccion: dto.direccion,
    estado: dto.estado,
    observaciones: dto.observaciones,
    foto: dto.foto,
    ubicacion: dto.lat !== null && dto.lng !== null ? { lat: dto.lat, lng: dto.lng } : null,
    creadaEn,
    actualizadaEn: dto.actualizada ? aFecha(dto.actualizada, 'actualizada') : creadaEn,
  };
}

Paso 2.2 · El repositorio HTTP con caché de lectura

Qué hacer. Implementa el puerto (data/visitas-http.repository.ts). En la lectura, valida el contrato antes de guardar en la caché y recurre a la caché solo si el error es de conectividad. Las escrituras exigen red; si tienen éxito, ajustan la caché.

/**
 * Implementación del puerto VisitasRepository: HTTP + CACHÉ DE LECTURA (ADR-002, offline.md).
 *
 * - Lectura: en línea guarda la respuesta; sin red (ErrorSinConexion / ErrorTiempoAgotado) devuelve
 *   lo último guardado marcado `desactualizado: true`. Sin red y sin caché, el error sube.
 * - Escritura: SOLO en línea (POST/PUT/DELETE no se reintentan ni se encolan). Si tiene éxito,
 *   la caché se actualiza para que la próxima lectura offline ya incluya el cambio.
 * - La caché guarda DTOs (modelo persistido ≠ entidad de dominio) y se mapea al leer.
 */
@Injectable({ providedIn: 'root' })
export class VisitasHttpRepository implements VisitasRepository {
  private readonly http = inject(HttpClient);
  private readonly api = inject(API_URL);
  private readonly cache = inject(CACHE_LOCAL);

  async listar(): Promise<ListaVisitas> {
    try {
      const respuesta = await firstValueFrom(this.http.get<unknown>(`${this.api}/visitas`));
      const visitas = aVisitas(respuesta); // valida el contrato ANTES de guardar en caché
      await this.cache.guardar(CLAVE_CACHE_VISITAS, respuesta as VisitaDto[]);
      return { visitas, desactualizado: false, sincronizadoEn: new Date() };
    } catch (e) {
      if (!esErrorDeConectividad(e)) throw e;
      const guardado = await this.cache.leer<VisitaDto[]>(CLAVE_CACHE_VISITAS);
      if (!guardado) throw e;
      return { visitas: aVisitas(guardado.valor), desactualizado: true, sincronizadoEn: new Date(guardado.guardadoEn) };
    }
  }

Deberías ver. Que un 500, una sesión expirada o datos inválidos no se disfrazan de «sin conexión»: solo ErrorSinConexion y ErrorTiempoAgotado activan la caché. El repositorio nunca ve un HttpErrorResponse: cuando el error llega al catch, el interceptor de errores ya lo tradujo (paso 3.3). La clave de la caché es versionada (visitas.lista.v1): si cambia la forma del DTO, sube a v2.

Decorador en la OVA, caché integrada en la referencia. La OVA envolvió el repositorio remoto con un decorador que cumple el mismo contrato. La referencia pone la caché dentro de VisitasHttpRepository porque una sola feature la usa y así el flujo se lee en un archivo. Con varias features con caché, el decorador evita repetir la lógica. Sea cual sea tu elección, va en docs/03-api-y-datos/offline.md.

Paso 2.3 · Por qué Preferences para la caché (ADR-002)

Qué hacer. Declara la caché como un puerto en core/storage/ y elige su adaptador en un ADR. En la referencia, el puerto CacheLocal tiene tres métodos (leer, guardar y limpiar, que se llama al cerrar sesión), lo implementa PreferencesCacheLocal sobre Capacitor Preferences y lo entrega el InjectionToken CACHE_LOCAL. Cuidado

Preferences no es almacenamiento seguro. Guarda en SharedPreferences (Android) o UserDefaults (iOS) sin cifrar. Sirve para la caché de lectura, nunca para tokens: por eso hay dos puertos, CacheLocal y TokenStore (sección 4). Y como la caché contiene datos de clientes, se borra al cerrar sesión.

3. El cliente HTTP único: cadena de interceptores

Ningún repositorio adjunta tokens, mide tiempos ni traduce errores. Todo eso ocurre una vez, en la cadena de interceptores, y su orden es una decisión de diseño.

Paso 3.1 · Registra el cliente una sola vez

Qué hacer. Registra HttpClient con sus interceptores en un único proveedor, core/di/core.providers.ts, y documenta el orden en el comentario.

/**
 * Raíz de composición de core/: EL cliente HTTP de la app y el arranque de la sesión.
 *
 * Orden de los interceptores (la petición baja en este orden; la respuesta sube al revés):
 *   correlation-id → errores → auth (token + refresh) → timeout → red
 * - errores va antes de auth: traduce el error FINAL (después del reintento).
 * - timeout va al final: cada intento tiene su propio límite.
 *
 * Los adaptadores de los puertos (TokenStore, CacheLocal, Camara, Ubicacion) no se registran
 * aquí: cada InjectionToken trae su factory (ver storage.tokens.ts y nativo.tokens.ts).
 */
export function provideCore(): EnvironmentProviders {
  return makeEnvironmentProviders([
    provideHttpClient(withInterceptors([correlationIdInterceptor, erroresInterceptor, authInterceptor, timeoutInterceptor])),
    provideAppInitializer(() => inject(SesionService).restaurar()),
  ]);
}

Paso 3.2 · Los cuatro interceptores

Qué hacer. Escribe cada interceptor como una función pequeña con una sola responsabilidad.

export const ENCABEZADO_CORRELACION = 'X-Correlation-Id';

/** Cada petición lleva un id único: permite seguirla en los logs de la app y del servidor. */
export const correlationIdInterceptor: HttpInterceptorFn = (req, next) =>
  next(req.clone({ setHeaders: { [ENCABEZADO_CORRELACION]: nuevoIdCorrelacion() } }));
/**
 * Frontera de errores: de aquí hacia arriba (repositorios, casos de uso, ViewModels) solo
 * circulan errores de dominio. Va justo después de correlation-id (antes de auth y timeout) para ver el error final, después del
 * reintento por refresh y del timeout.
 */
export const erroresInterceptor: HttpInterceptorFn = (req, next) =>
  next(req).pipe(catchError((e: unknown) => throwError(() => mapearErrorHttp(e))));
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  if (esRutaDeAutenticacion(req.url)) return next(req);
  const sesion = inject(SesionService);
  const tokenUsado = sesion.accessToken;
  if (!tokenUsado) return next(req);

  return next(conBearer(req, tokenUsado)).pipe(
    catchError((error: unknown) => {
      if (!(error instanceof HttpErrorResponse) || error.status !== 401) return throwError(() => error);
      return from(sesion.refrescar(tokenUsado)).pipe(switchMap((nuevo) => next(conBearer(req, nuevo))));
    }),
  );
};
/** Tiempo límite por petición. Se cambia por llamada con `new HttpContext().set(TIEMPO_LIMITE_MS, n)`. */
export const TIEMPO_LIMITE_MS = new HttpContextToken<number>(() => 10_000);

/**
 * Ninguna petición queda sin límite. `timeout(n)` mide el tiempo entre eventos: desde el envío
 * hasta la respuesta. Va al final de la cadena: cada intento (también el reintento tras el
 * refresh) tiene su propio límite. El TimeoutError lo traduce `erroresInterceptor`.
 */
export const timeoutInterceptor: HttpInterceptorFn = (req, next) =>
  next(req).pipe(timeout(req.context.get(TIEMPO_LIMITE_MS)));

Deberías ver. Por qué el orden importa:

  • Correlación primero: el reintento tras el refresh conserva el mismo X-Correlation-Id y se puede seguir en los logs.
  • Errores envuelve a auth y a timeout: traduce el error final, después del reintento. Por eso va justo después de la correlación, que es la única que va antes.
  • Auth reintenta una sola vez por la forma del código: el reintento está después del catchError, así que su error no vuelve a entrar ahí. No hace falta un contador.
  • Timeout al final: cada intento, incluido el reintento, tiene sus propios 10 segundos.
  • Las rutas `/auth/*` no llevan token ni disparan refresh (esRutaDeAutenticacion): así no hay ciclos.

Paso 3.3 · De errores HTTP a errores de dominio

Qué hacer. Escribe una función pura (core/network/mapear-error-http.ts) que traduzca cada falla técnica a un error de dominio. Es la frontera: de ahí hacia arriba nadie ve un HttpErrorResponse.

export function mapearErrorHttp(e: unknown): ErrorDominio {
  if (e instanceof ErrorDominio) return e;
  if (e instanceof TimeoutError) return new ErrorTiempoAgotado();
  if (e instanceof HttpErrorResponse) {
    if (e.status === 0) return new ErrorSinConexion();
    if (e.status === 401) return new ErrorSesionExpirada();
    if (e.status === 404) return new ErrorNoEncontrado();
    if (e.status === 400 || e.status === 422) {
      const detalle = typeof e.error?.error === 'string' ? e.error.error : 'Revisa los datos enviados.';
      return new ErrorValidacion(detalle);
    }
    if (e.status >= 500) return new ErrorServidor();
  }
  return new ErrorInesperado();
}

4. Sesión y tokens

El interceptor adjunta el token, pero no es su dueño. Un solo servicio, SesionService, sabe dónde están los tokens, cómo se renuevan y qué pasa cuando ya no sirven.

Paso 4.1 · Dónde vive cada token (ADR-004)

DatoVidaDónde vive en la referenciaPara qué

refreshToken7 díasAlmacén seguroPOST /auth/refresh para un access token nuevo

Qué hacer. Declara el puerto TokenStore (leer, guardar y borrar el par de tokens) e impleméntalo con un plugin de almacenamiento seguro; el InjectionToken TOKEN_STORE lo entrega y las pruebas lo cambian por TokenStoreFalso. SesionService es el único que lo lee o escribe. El adaptador de la referencia es core/storage/secure-token-store.ts:

/**
 * Adaptador de TokenStore sobre @aparajita/capacitor-secure-storage:
 * iOS → Keychain; Android → AES-GCM con llave del Android Keystore.
 * En el navegador el plugin usa localStorage SIN cifrar: solo sirve para depurar (ADR-004).
 */
export class SecureTokenStore implements TokenStore {
  async leer(): Promise<TokensSesion | null> {
    const valor = await SecureStorage.get(CLAVE);
    return esTokensSesion(valor) ? valor : null;
  }

  async guardar(tokens: TokensSesion): Promise<void> {
    await SecureStorage.set(CLAVE, { accessToken: tokens.accessToken, refreshToken: tokens.refreshToken });
  }

Una diferencia con la OVA. La OVA propuso el access token solo en memoria. La referencia guarda el par de tokens como una sola entrada en el almacén seguro y además mantiene el access token en memoria para el interceptor. El ADR-004 lo justifica: una entrada atómica y una sesión que se restaura al abrir la app aunque no haya señal. Las dos opciones cumplen la regla del marco: ningún token toca localStorage ni Preferences.

Cuidado

En el navegador (npm start) el plugin guarda en localStorage sin cifrar: sirve para depurar, no para afirmar que la app es segura. La seguridad se verifica en el dispositivo; dilo así en tu análisis.

Paso 4.2 · El refresh se hace una sola vez

Qué hacer. Si varias peticiones reciben 401 al mismo tiempo, todas deben compartir un refresh. La referencia guarda la promesa en curso y la reutiliza.

  /**
   * Devuelve un access token vigente. Si `tokenRechazado` ya no es el actual (otra petición
   * renovó primero), reutiliza el nuevo sin volver a llamar a la API.
   * Varias peticiones con 401 simultáneo comparten UNA sola llamada a /auth/refresh.
   */
  refrescar(tokenRechazado?: string): Promise<string> {
    const actual = this.accessToken;
    if (actual && tokenRechazado && actual !== tokenRechazado) return Promise.resolve(actual);
    this.refrescoEnCurso ??= this.pedirNuevoAccessToken().finally(() => (this.refrescoEnCurso = null));
    return this.refrescoEnCurso;
  }
  private async pedirNuevoAccessToken(): Promise<string> {
    const actuales = this.tokens;
    if (!actuales) throw new ErrorSesionExpirada();
    try {
      const respuesta = await firstValueFrom(
        this.httpSinInterceptores
          .post<{ accessToken?: unknown }>(`${this.api}/auth/refresh`, { refreshToken: actuales.refreshToken })
          .pipe(timeout(TIEMPO_LIMITE_REFRESH_MS)),
      );
      if (typeof respuesta.accessToken !== 'string') throw new ErrorSesionExpirada();
      const nuevos: TokensSesion = { accessToken: respuesta.accessToken, refreshToken: actuales.refreshToken };
      await this.tokenStore.guardar(nuevos);
      this.establecer(nuevos);
      return nuevos.accessToken;
    } catch (e) {
      const rechazado = e instanceof ErrorSesionExpirada || (e instanceof HttpErrorResponse && (e.status === 401 || e.status === 400));
      if (rechazado) {
        await this.limpiarLocal();
        this.expiradaSubject.next();
        throw new ErrorSesionExpirada();
      }
      // Sin red o servidor caído: NO se cierra la sesión; el error sube ya traducido.
      throw mapearErrorHttp(e);
    }
  }
  GET /visitas (Bearer A)    ──► 401 ┐
  GET /visitas/s7 (Bearer A) ──► 401 ├──► refrescar(A) ──► POST /auth/refresh   (UNA sola vez)
                                     ┘               │
        ┌────────────────────────────────────────────┼─────────────────────────┐
        ▼                                            ▼                         ▼
     200 {accessToken: B}                          401 o 400 (rechazado)     sin red o timeout
     guarda B en TokenStore                        borra tokens y caché      NO cierra la sesión
     reintenta cada GET UNA vez                    emite expirada$ → /login  ErrorSinConexion

Por qué `httpSinInterceptores`. Las llamadas a /auth/refresh y /auth/logout salen por un HttpClient construido sobre HttpBackend, que no pasa por la cadena. Si pasaran por el interceptor de autenticación, un 401 del refresh dispararía otro refresh.

Paso 4.3 · Cierre de sesión y sesión expirada

Qué hacer. SesionService.cerrar() intenta POST /auth/logout para revocar el refresh token (si no hay red, sigue) y siempre borra los tokens del almacén seguro y la caché. Cuando el refresh es rechazado, el servicio emite expirada$; la capa de red no conoce rutas, así que es el shell (app.component.ts) el que navega a /login con navigateRoot y muestra «Tu sesión expiró. Ingresa de nuevo.».

Deberías ver. Tras cerrar sesión, /login como raíz (atrás no vuelve a la lista) y, en el almacenamiento local del navegador, ni la sesión ni la caché de visitas: un teléfono compartido no debe mostrar las visitas del técnico anterior.

5. Presentación: un ViewModel por pantalla (ADR-001)

La pantalla dibuja un objeto de estado y emite intenciones. El ViewModel decide la fase siguiente; la plantilla solo la recorre.

Paso 5.1 · Estado inmutable con fases explícitas

Qué hacer. Modela el estado como un solo objeto con un campo fase, guárdalo en un BehaviorSubject privado y exponlo como signal de solo lectura. Toda transición crea un objeto nuevo con { ...previo, cambio }. El ViewModel se provee en el componente: nace y muere con la pantalla.

/** Fases de la pantalla: exactamente una a la vez (01-arquitectura/feature-visitas.md). */
export type FaseLista = 'cargando' | 'cargado' | 'vacio' | 'error' | 'offline';

/** Estado inmutable de la lista. La pantalla renderiza SOLO a partir de este objeto. */
export interface EstadoLista {
  readonly fase: FaseLista;
  readonly visitas: readonly Visita[];
  readonly resumen: ResumenVisitas;
  /** Mensaje del estado `error` (bloqueante). */
  readonly error: string | null;
  /** Cuándo se sincronizó; en `offline` es la fecha de la caché. */
  readonly sincronizadoEn: Date | null;
  /** Mensaje transitorio (toast): eliminada, no se pudo eliminar, no se pudo refrescar... */
  readonly aviso: string | null;
}
@Injectable()
export class VisitasListaViewModel {
  private readonly listarVisitas = inject(ListarVisitas);
  private readonly eliminarVisita = inject(EliminarVisita);
  private readonly estado$ = new BehaviorSubject<EstadoLista>(ESTADO_LISTA_INICIAL);
  private ultimaCarga = 0;
  private activo = true;

  readonly estado = toSignal(this.estado$, { requireSync: true });

  constructor() {
    inject(DestroyRef).onDestroy(() => (this.activo = false));
  }

  async cargar(): Promise<void> {
    const carga = ++this.ultimaCarga;
    const previo = this.estado$.value;
    const hayDatosEnPantalla = previo.visitas.length > 0;
    if (!hayDatosEnPantalla) this.emitir({ ...previo, fase: 'cargando', error: null });
    try {
      const lista = await this.listarVisitas.ejecutar();
      if (carga === this.ultimaCarga) this.emitir(estadoDesde(lista));
    } catch (e) {
      if (carga !== this.ultimaCarga) return;
      // Con datos en pantalla, un fallo al refrescar no borra la lista: solo avisa.
      this.emitir(
        hayDatosEnPantalla
          ? { ...this.estado$.value, aviso: mensajeDeError(e) }
          : { ...ESTADO_LISTA_INICIAL, fase: 'error', error: mensajeDeError(e) },
      );
    }
  }

Paso 5.3 · Formulario reactivo con un validador propio

Qué hacer. El formulario es estado de la vista; las reglas son del dominio. Reutiliza los límites del dominio en los Validators y agrega un validador propio para lo que Angular no trae.

/**
 * Validador propio: rechaza un texto que solo tiene espacios («   » pasaría `required` y `minLength`).
 * El texto vacío lo valida `Validators.required`, no este.
 */
export const sinSoloEspacios: ValidatorFn = (control: AbstractControl): ValidationErrors | null =>
  typeof control.value === 'string' && control.value.length > 0 && control.value.trim().length === 0
    ? { soloEspacios: true }
    : null;
  protected readonly form = this.fb.group({
    cliente: ['', [Validators.required, Validators.minLength(LIMITES_VISITA.clienteMin), Validators.maxLength(LIMITES_VISITA.clienteMax), sinSoloEspacios]],
    direccion: ['', Validators.maxLength(LIMITES_VISITA.direccionMax)],
    estado: this.fb.control<EstadoVisita>('pendiente', Validators.required),
    observaciones: ['', Validators.maxLength(LIMITES_VISITA.observacionesMax)],
  });

Deberías ver. Tres niveles sin duplicar reglas:

  • El formulario da retroalimentación inmediata con los mismos límites del dominio (LIMITES_VISITA) y con sinSoloEspacios.
  • La regla «realizada exige foto» vive solo en validarDatosVisita: el caso de uso lanza ErrorValidacion y el ViewModel del formulario muestra su mensaje.
  • VisitaFormViewModel.guardar() ignora un segundo toque mientras la fase es guardando: es la protección contra el doble envío.

Qué hacer. Declara todas las rutas en app.routes.ts, con carga diferida, el guard en el grupo protegido y los providers de la feature en la ruta. Los guards son funciones de una línea sobre SesionService.autenticado().

  • El guard en el grupo protege cualquier pantalla nueva bajo /visitas sin tocarla.

Paso 7.1 · Todos los valores en un archivo

Qué hacer. Crea core/theme/tokens.scss con tus tokens (color, espaciado, radios, tipografía en rem y alturas mínimas) y mapea a ellos la paleta de Ionic. Las pantallas usan solo var(--prefijo-…); el tema oscuro cambia valores, no componentes.

9.2 · Cómo suena un párrafo argumentado

Un argumento técnico tiene cuatro piezas: decisión, razón, alternativa descartada y fuente. Este párrafo usa la Bitácora solo para mostrar la forma:

Para la integración con la API adoptamos un cliente HTTP único con cuatro interceptores
funcionales registrados en un solo proveedor: correlación, traducción de errores,
autenticación con refresh y tiempo límite. El orden es deliberado: la traducción de errores
envuelve a la autenticación para que la pantalla reciba el error final, después del único
reintento tras el refresh (Angular, s. f.). Descartamos adjuntar el token en cada repositorio
porque duplica la lógica y deja rutas sin protección. El refresh token se guarda en Keychain
y Keystore mediante un puerto propio, nunca en Preferences, que almacena en texto plano
(Capacitor, s. f.; OWASP, 2024).
