Unidad 3 · Calidad y release

Arquitectura de calidad y de entrega: nativo, pruebas y despliegue

Una app no está terminada cuando funciona en tu teléfono, sino cuando usa el hardware sin acoplarse a él, pide permisos con respeto, protege lo que guarda, se prueba sin dispositivo, se firma con identidades custodiadas y se observa en producción. Esta unidad convierte esas propiedades en decisiones de arquitectura verificables.

1

Integrar cámara, geolocalización, push, biometría y almacenamiento seguro como adaptadores de puertos del dominio, sin que el negocio importe Capacitor.

2

Diseñar el flujo de permisos just-in-time con sus estados y las diferencias reales entre Android e iOS.

3

Aplicar las reglas de seguridad móvil del marco de gobierno (secretos, TLS y pinning, datos en reposo, tokens, hardening) y verificarlas con una lista de chequeo.

4

Fijar presupuestos de rendimiento medibles y elegir la técnica que corresponde a cada síntoma.

5

Diseñar una estrategia de pruebas en pirámide con fakes de los puertos, portable entre Jasmine/Karma y Vitest, con cobertura ≥ 80 % en dominio y ViewModels.

6

Planear el release completo: íconos y splash, versionado, firma, AAB/APK/IPA, despliegue escalonado, CI/CD y observabilidad.

2. Plugins nativos como adaptadores

Capacitor es un puente: tu TypeScript llama a una API basada en promesas y Capacitor la despacha a Kotlin/Java o Swift. La pregunta de arquitectura no es cómo llamar al plugin —eso cabe en tres líneas—, sino quién tiene permitido llamarlo.

Regla de dependencias (01 Arquitectura del marco). El dominio tiene cero dependencias hacia afuera. Un plugin es infraestructura, igual que una base de datos: el dominio declara un puerto en su propio idioma y la capa de datos lo implementa con un adaptador.

2.1 Por qué el dominio no importa Capacitor

  • Testabilidad: el caso de uso que depende del puerto Camara se prueba en milisegundos con un fake; el que importa @capacitor/camera necesita un teléfono.
  • Volatilidad: las APIs de los plugins cambian entre versiones mayores y la biometría depende de plugins comunitarios; el cambio queda encerrado en un archivo.
  • Lenguaje: el dominio habla de PermisoDenegadoError('camara'), no de PermissionState ni de códigos de Android.

2.3 Puerto, adaptador y caso de uso

CapturarEvidencia tiene una regla de negocio clara: la foto es obligatoria y la ubicación es de mejor esfuerzo. Sin permiso de cámara no hay evidencia; sin ubicación (por permiso, señal o tiempo agotado) la visita se guarda igual, sin coordenadas.

// features/visitas/domain/ — TypeScript puro: ni Angular ni Capacitor.
export type Recurso = 'camara' | 'ubicacion';
export type EstadoPermiso = 'concedido' | 'preguntable' | 'denegado';
export class PermisoDenegadoError extends Error {
  constructor(readonly recurso: Recurso, readonly definitivo: boolean) { super(`Sin permiso: ${recurso}`); }
}
export class UbicacionNoDisponibleError extends Error {}

export interface Foto { readonly ruta: string; readonly formato: string; }
export interface Coordenadas { readonly latitud: number; readonly longitud: number; readonly precisionMetros: number; }
export interface Reloj { ahora(): Date; }
export interface Camara { permiso(): Promise<EstadoPermiso>; tomarFoto(): Promise<Foto>; }
export interface Ubicacion { permiso(): Promise<EstadoPermiso>; actual(): Promise<Coordenadas>; }
// features/visitas/data/ — el ÚNICO archivo de la feature que conoce @capacitor/camera.
import { Injectable } from '@angular/core';
import type { PermissionState } from '@capacitor/core';
import { Camera, CameraResultType, CameraSource } from '@capacitor/camera';

export function aEstado(s: PermissionState | 'limited'): EstadoPermiso {
  if (s === 'granted' || s === 'limited') return 'concedido';
  return s === 'denied' ? 'denegado' : 'preguntable';     // 'prompt' o 'prompt-with-rationale'
}

@Injectable()
export class CamaraCapacitor implements Camara {
  async permiso(): Promise<EstadoPermiso> { return aEstado((await Camera.checkPermissions()).camera); }

  async tomarFoto(): Promise<Foto> {
    let estado = await this.permiso();
    if (estado === 'preguntable') {
      estado = aEstado((await Camera.requestPermissions({ permissions: ['camera'] })).camera);
    }
    if (estado !== 'concedido') throw new PermisoDenegadoError('camara', estado === 'denegado');
    const foto = await Camera.getPhoto({
      source: CameraSource.Camera, resultType: CameraResultType.Uri,   // archivo, NO base64
      quality: 70, width: 1600,
    });
    return { ruta: foto.webPath ?? '', formato: foto.format };
  }
}
export interface Evidencia { readonly foto: Foto; readonly ubicacion: Coordenadas | null; readonly capturadaEn: Date; }

export class CapturarEvidencia {
  constructor(private readonly camara: Camara, private readonly ubicacion: Ubicacion, private readonly reloj: Reloj) {}

  async ejecutar(): Promise<Evidencia> {
    const foto = await this.camara.tomarFoto();        // obligatoria: si falla, se propaga
    let coordenadas: Coordenadas | null = null;
    try {
      coordenadas = await this.ubicacion.actual();     // mejor esfuerzo
    } catch (e) {
      const esperado = e instanceof PermisoDenegadoError || e instanceof UbicacionNoDisponibleError;
      if (!esperado) throw e;                          // un bug NO se traga en silencio
    }
    return { foto, ubicacion: coordenadas, capturadaEn: this.reloj.ahora() };
  }
}

La composición vive en la frontera de la feature (visitas.providers.ts): allí se declaran los InjectionToken CAMARA y UBICACION, se enlazan a sus adaptadores y se construye el caso de uso con useFactory + inject(). Los tokens de Angular no entran al dominio. Tres decisiones más son de arquitectura, no de estilo: la foto se toma antes que la ubicación (sin foto no se molesta al usuario con un segundo permiso); el adaptador traduce los estados de Capacitor al vocabulario del dominio; y el caso de uso solo absorbe los errores que la regla declara esperables.

Consejo. UbicacionCapacitor sigue el mismo molde con Geolocation.getCurrentPosition({ enableHighAccuracy: true, timeout: 8000, maximumAge: 60000 }). Si el usuario concedió solo la ubicación aproximada, checkPermissions() devuelve coarseLocation: 'granted': trátalo como concedido y deja que precisionMetros le cuente la verdad al dominio.

3. Permisos just-in-time

La regla del marco (security-rules.md) es tajante: el mínimo de permisos, justo cuando se necesitan y con una justificación clara; nunca «por si acaso». Pedirlo todo al arrancar produce lo contrario de lo que se busca: el usuario niega por reflejo, en Android dos negativas bastan para que el sistema no vuelva a mostrar el diálogo, y las tiendas lo revisan (Apple rechaza textos de propósito vagos; Google Play exige justificar la ubicación en segundo plano).

3.1 El flujo

  El usuario toca «Agregar evidencia»   ← el momento en que el permiso tiene sentido
                   │
           permiso() ──── concedido ───────────────────────────────► tomarFoto()
                   │
                   ├──── preguntable ──► pantalla propia «¿Para qué la cámara?»
                   │                      [Continuar]           [Ahora no] ─► estado degradado
                   │                          ▼
                   │                 diálogo del sistema ── concede ──► tomarFoto()
                   │                          └──────────── niega ────► explicar, reintentar luego
                   │
                   └──── denegado ──► explicar lo que se pierde + botón «Abrir ajustes»

3.2 El ViewModel decide; la vista pinta

La presentación puede depender de los puertos del dominio (nunca de los adaptadores): el ViewModel consulta permiso() para mostrar la justificación antes del diálogo del sistema y traduce los errores del caso de uso a un estado de pantalla inmutable.

// features/visitas/presentation/registro-visita.viewmodel.ts
export type EstadoCaptura = { tipo: 'inicial' } | { tipo: 'capturando' } | { tipo: 'justificar'; recurso: Recurso }
  | { tipo: 'lista'; evidencia: Evidencia } | { tipo: 'error'; mensaje: string }
  | { tipo: 'sin-permiso'; recurso: Recurso; definitivo: boolean };

@Injectable()
export class RegistroVisitaViewModel {
  private readonly camara = inject(CAMARA);              // puerto del dominio: permitido
  private readonly capturar = inject(CapturarEvidencia);
  private readonly _estado = signal<EstadoCaptura>({ tipo: 'inicial' });
  readonly estado = this._estado.asReadonly();           // la vista lee, nunca escribe

  async agregarEvidencia(): Promise<void> {              // pantalla propia ANTES del diálogo del SO
    if ((await this.camara.permiso()) === 'preguntable') this._estado.set({ tipo: 'justificar', recurso: 'camara' });
    else await this.capturarAhora();
  }

  async capturarAhora(): Promise<void> {                 // tras «Continuar», o si ya está concedido/denegado
    this._estado.set({ tipo: 'capturando' });
    try {
      this._estado.set({ tipo: 'lista', evidencia: await this.capturar.ejecutar() });
    } catch (e) {
      this._estado.set(e instanceof PermisoDenegadoError
        ? { tipo: 'sin-permiso', recurso: e.recurso, definitivo: e.definitivo }
        : { tipo: 'error', mensaje: 'No se pudo capturar la evidencia.' });
    }
  }
}

4. Seguridad móvil

Verdad incómoda de una app híbrida: el APK es un archivo comprimido y tu JavaScript se lee en assets/public/. Nada de lo que viaja dentro del binario es secreto, por mucho que se minifique.

4.1 Secretos y transporte

Si una llave de terceros (mapas, correo, IA) permite gastar dinero o leer datos, no va en la app: va en el backend, que la app llama con el token del usuario. Keystore, contraseñas y certificados viven en los secretos del CI y en una bóveda, nunca en environment.ts.

TLS evita que alguien lea el tráfico; el pinning evita que alguien con un certificado «válido» (instalado en el equipo o emitido por error) suplante tu API. En una híbrida no se hace desde Angular: el WebView no expone a JavaScript la validación del certificado. Se hace en la capa nativa y las llamadas sensibles viajan por la pila HTTP nativa.

<!-- res/xml/network_security_config.xml · manifest: android:networkSecurityConfig="@xml/network_security_config" -->
<network-security-config>
  <base-config cleartextTrafficPermitted="false" />
  <domain-config>
    <domain includeSubdomains="true">api.bitacora.example</domain>
    <pin-set expiration="2027-06-30">
      <pin digest="SHA-256">PIN_PRINCIPAL_BASE64=</pin>
      <pin digest="SHA-256">PIN_DE_RESPALDO_BASE64=</pin>
    </pin-set>
  </domain-config>
</network-security-config>

En capacitor.config.ts el build de release lleva plugins: { CapacitorHttp: { enabled: true } } (fetch y XHR por la pila nativa, que sí respeta el pin-set) y nunca server.url ni server.cleartext: true, que son del live reload.

Cuidado

Un pinning sin pin de respaldo ni expiración es una bomba de tiempo: si el backend rota su certificado, toda instalación queda sin servicio hasta publicar otra versión. En iOS requiere código o plugin nativo; documenta la decisión en un ADR.

4.2 Datos en reposo, tokens y hardening

  • Tokens de acceso y de refresco solo en almacenamiento seguro (Keychain / Keystore); nunca en localStorage, Preferences ni SQLite sin cifrar. La biometría solo abre la puerta.
  • Fotos de evidencia en el directorio privado de la app, no en la galería; caché offline sin PII que la pantalla no use.
  • Cierre de sesión: borra tokens y caché sensible, y cancela las peticiones en curso.
  • Build de release: minifyEnabled true (R8) en la capa nativa y ng build de producción en la web; minificar no es cifrar.
  • Sin rastros de depuración: nada de console.log con datos ni tokens; webContentsDebuggingEnabled apagado y android:allowBackup="false" si hay datos sensibles.

4.3 Checklist de seguridad antes de cada release

  • Tokens y secretos solo en almacenamiento seguro (Keychain / Keystore).
  • Datos sensibles locales cifrados y borrados al cerrar sesión; sin PII innecesaria.
  • Todo el tráfico por TLS; sin cleartext ni server.url en el build de release.
  • Pinning activo en autenticación (y pagos, si los hay), con pin de respaldo.
  • Permisos mínimos, pedidos just-in-time; ninguno declarado sin uso.
  • Build ofuscado/minificado, sin logs de depuración ni banderas de debug.
  • Ninguna llave ni credencial en el bundle o en el repositorio.
  • npm audit ejecutado y SDK de terceros revisados por los datos que recolectan.

5.2 Buenas prácticas del WebView

  • Anima solo transform y opacity: se componen en la GPU sin recalcular el layout.
  • DOM poco profundo y track en cada @for, para que Angular reutilice nodos.
  • Imágenes redimensionadas, en WebP y con loading="lazy"; nada de scripts externos innecesarios.
  • Fotos por URI (CameraResultType.Uri), nunca en base64: una foto de 12 MP son megabytes de texto en memoria.
  • Trabajo pesado (comprimir, procesar) fuera del hilo principal: Web Worker o plugin nativo.

6. Estrategia de pruebas

testing-strategy.md del marco fija tres cosas no negociables: qué se prueba en cada nivel, cuánto de cada nivel y cómo se nombran las pruebas.

                    ┌───────────┐  ~10 %  Integración / E2E: flujo completo en
                    │    E2E    │         emulador o dispositivo (nocturno y pre-release)

6.1 Fakes de los puertos y runners

Un fake es una implementación real pero simplificada de una interfaz (Meszaros lo distingue del stub, que solo devuelve valores, y del mock, que verifica llamadas). Como el dominio depende de Camara y no de @capacitor/camera, el fake es una clase de seis líneas: no hay que simular módulos de npm ni hardware. El marco pide simular solo dependencias directas y probar comportamiento y transiciones de estado, no detalles de implementación.

AspectoJasmine + KarmaVitest
Qué esJasmine estructura y afirma; Karma ejecuta en un navegador realRunner y aserciones en uno; DOM simulado o modo navegador
En AngularEl clásico, el que pide el aula; Karma está deprecado desde 2023Predeterminado en proyectos nuevos desde Angular 21

Común a ambosdescribe, it, beforeEach, expect, toBe, toEqual, toBeNull, TestBedEl mismo subconjunto

Pruebas portables. Usa solo el subconjunto común y fakes propios; captura los rechazos con try/catch en lugar de expectAsync o rejects. Las mismas pruebas corren con el runner que traiga tu proyecto, y migrar de Karma a Vitest no obliga a reescribirlas.

6.2 Nombres, cobertura y CI

  • Nombres unidad_condicion_resultado: capturarEvidencia_sinPermisoDeCamara_lanzaPermisoDenegado. Si falla, se lee qué regla se rompió.
  • Arrange-Act-Assert, una afirmación lógica por prueba; sin red real ni esperas de reloj: el tiempo entra por el puerto Reloj.
  • Cobertura: piso de 80 % en `domain/` y en los ViewModels, no un promedio global. Una línea cubierta no es un comportamiento probado.
  • CI: unitarias y de UI en cada PR con un solo comando, npm run test:ci (ng test --no-watch --code-coverage --browsers=ChromeHeadless con Karma; ng test --no-watch --coverage con Vitest).

6.3 Ejemplo: CapturarEvidencia y su ViewModel con fakes

export class FakeCamara implements Camara {
  llamadas = 0;
  constructor(private readonly r: Foto | Error, private readonly estado: EstadoPermiso = 'concedido') {}
  async permiso(): Promise<EstadoPermiso> { return this.estado; }
  async tomarFoto(): Promise<Foto> { this.llamadas++; if (this.r instanceof Error) throw this.r; return this.r; }
}
export class FakeUbicacion implements Ubicacion {
  llamadas = 0;
  constructor(private readonly r: Coordenadas | Error) {}
  async permiso(): Promise<EstadoPermiso> { return 'concedido'; }
  async actual(): Promise<Coordenadas> { this.llamadas++; if (this.r instanceof Error) throw this.r; return this.r; }
}
// Captura el rechazo sin APIs propias del runner (ni expectAsync ni rejects).
export async function errorDe(p: Promise<unknown>): Promise<unknown> {
  try { await p; return undefined; } catch (e) { return e; }
}
describe('CapturarEvidencia', () => {
  const FOTO: Foto = { ruta: 'evidencias/visita-1.jpeg', formato: 'jpeg' };
  const NEIVA: Coordenadas = { latitud: 2.9273, longitud: -75.2819, precisionMetros: 12 };
  const reloj: Reloj = { ahora: () => new Date('2026-10-23T23:00:00Z') };
  const sinCamara = () => new FakeCamara(new PermisoDenegadoError('camara', false));

  it('capturarEvidencia_conAmbosPermisos_devuelveFotoUbicacionYFecha', async () => {
    const evidencia = await new CapturarEvidencia(new FakeCamara(FOTO), new FakeUbicacion(NEIVA), reloj).ejecutar();
    expect(evidencia).toEqual({ foto: FOTO, ubicacion: NEIVA, capturadaEn: reloj.ahora() });
  });

  it('capturarEvidencia_sinPermisoDeUbicacion_guardaSinCoordenadas', async () => {
    const ubicacion = new FakeUbicacion(new PermisoDenegadoError('ubicacion', true));
    const evidencia = await new CapturarEvidencia(new FakeCamara(FOTO), ubicacion, reloj).ejecutar();
    expect(evidencia.ubicacion).toBeNull();
  });

  it('capturarEvidencia_sinPermisoDeCamara_lanzaPermisoDenegado', async () => {
    const error = await errorDe(new CapturarEvidencia(sinCamara(), new FakeUbicacion(NEIVA), reloj).ejecutar());
    expect(error instanceof PermisoDenegadoError).toBe(true);
  });

  it('capturarEvidencia_sinPermisoDeCamara_noPideUbicacion', async () => {
    const ubicacion = new FakeUbicacion(NEIVA);
    await errorDe(new CapturarEvidencia(sinCamara(), ubicacion, reloj).ejecutar());
    expect(ubicacion.llamadas).toBe(0);
  });
});

El ViewModel se prueba igual: TestBed.configureTestingModule con RegistroVisitaViewModel, { provide: CAMARA, useValue: new FakeCamara(FOTO, 'preguntable') } y un caso de uso falso, y se afirma sobre vm.estado(); por ejemplo, agregarEvidencia_conPermisoPreguntable_muestraJustificacion espera { tipo: 'justificar', recurso: 'camara' }. TestBed funciona igual con ambos runners.

Los adaptadores y el flujo completo se validan en dispositivos: Firebase Test Lab ejecuta la app en una matriz de equipos reales (incluida la prueba Robo, que la recorre sin escribir código) y Appium automatiza el flujo sobre el binario. Lo que no automatices se documenta con la plantilla de caso de prueba de la sección 04 del marco. Mínimo antes de H3: el flujo de permisos con concedido, negado una vez y negado definitivo, en Android.

7.4 Publicación: escalonar, forzar y revertir

  • Pistas y despliegue escalonado: interna → prueba cerrada → producción al 5 % → 20 % → 50 % → 100 %; el porcentaje limita el daño de un defecto. Apple ofrece el equivalente como phased release de siete días.
  • Cuentas personales nuevas de Play: deben pasar una prueba cerrada con testers durante 14 días antes de producción; planéalo o documenta la simulación.
  • Actualización forzada: bandera remota versionMinimaSoportada; si la app es más vieja, bloquea con un enlace a la tienda. Se sube ante un cambio de API incompatible o una corrección crítica.
  • Rollback en móvil no es volver atrás: no se «despublica» hacia una versión anterior en los equipos que ya actualizaron. Ante el disparador (crash-free < 99,5 %, ANR o bug crítico) se detiene el despliegue y se avanza con un build de número mayor, aunque lleve el código anterior.
  • Banderas de funcionalidad: el único rollback instantáneo; apagarla desactiva la función sin pasar por la tienda.

8.1 Observabilidad: saber qué pasa sin adivinar

Una híbrida falla en dos capas. Un fallo nativo cierra la app y lo ve cualquier reportador de crashes; un error de JavaScript deja la app abierta con la pantalla muerta y nadie se entera si no lo reportas. Por eso el ErrorHandler de Angular se conecta al reportador a través de un puerto:

@Injectable()
export class ReporteErroresHandler implements ErrorHandler {
  private readonly reportador = inject(REPORTADOR_FALLOS);   // puerto: Crashlytics, Sentry u otro
  handleError(error: unknown): void {
    this.reportador.registrar(error, { ruta: location.pathname });   // contexto, nunca PII
  }
}
// app.config.ts → { provide: ErrorHandler, useClass: ReporteErroresHandler }
  • Crash-free ≥ 99,5 % en sesiones y usuarios; caer por debajo es disparador de rollback. ANR bajo el umbral de la plataforma y embudo clave sin regresión frente al release anterior.
  • Trazas legibles: sube el mapping.txt de R8, los dSYM de iOS y los source maps ocultos de Angular ("sourceMap": { "scripts": true, "hidden": true }).
  • Analítica sin PII: eventos definidos de antemano (visita_registrada con tiene_foto; permiso_respondido con recurso y resultado); ni nombres, ni correos, ni coordenadas.
  • Banderas de funcionalidad: toda función riesgosa detrás de una bandera remota, apagada por defecto en producción, con dueño y fecha de retiro.

Consejo. permiso_respondido responde una pregunta de arquitectura con datos: si después de tu pantalla de justificación la mayoría niega la ubicación, el problema no es el usuario, es el momento o el texto con que la pides.

9. Errores comunes

  1. Importar `@capacitor/*` en el dominio o en el componente. El caso de uso deja de probarse sin teléfono y un cambio del plugin se propaga a toda la feature.
  2. Pedir todos los permisos al arrancar o declararlos «por si acaso». El usuario niega por reflejo, la tienda lo observa y el checklist lo marca.
  3. Un bucle de diálogos tras una negativa definitiva. El sistema ya no muestra el diálogo y la app parece rota; la salida es explicar y ofrecer los ajustes.
  4. Guardar el token en `Preferences` o `localStorage`. Es texto plano; el token va en almacenamiento seguro.
  5. Creer que un secreto en `environment.prod.ts` está protegido. El APK se descomprime en segundos; las llaves de terceros van en el backend.
  6. Fotos en base64 dentro del estado. Memoria disparada y scroll a saltos en equipos modestos; se trabaja con la URI del archivo. (La app de referencia Bitácora de Campo guarda solo una miniatura reducida en su caché de lectura, como simplificación didáctica declarada; una app en producción guarda la foto como archivo y referencia su URI).
  7. Simular el plugin con utilidades del runner en vez de fakes del puerto. Las pruebas quedan atadas a Jasmine o a Vitest y al detalle de implementación.
  8. Perseguir 100 % de cobertura global. Lo exigible es 80 % en dominio y ViewModels, con pruebas que afirman comportamiento.
  9. Dejar `server.url` o `cleartext: true` del live reload en el release. La app instalada apunta al portátil del desarrollador o acepta HTTP plano.
  10. Subir el keystore al repositorio, reutilizar el número de build o pensar el rollback como en un backend. Identidad expuesta, subida rechazada y usuarios atrapados en la versión defectuosa.

11. Cierre y fuentes

Lo esencial de la unidad cabe en una frase: la calidad y la entrega también se diseñan. Los plugins entran por puertos, los permisos se piden cuando tienen sentido, la seguridad parte de que el binario es público, el rendimiento tiene números, las pruebas no necesitan un teléfono y el release es una cadena de identidades custodiadas que termina en observación.

Para H3 (dom 1-nov), la memoria técnica muestra estas decisiones con evidencia: estrategia de pruebas con cobertura por carpeta, checklist de seguridad, firma y binario, pipeline (real o diseñado) y cómo observarás la app publicada.
